## Assessment

Do not release. The new persistence paths can double-apply historical answers, lose earned XP and later flashcard grades, restore spent shields, and recompute ability using the wrong item difficulty. The supplied tests do not cover these failure scenarios.

## Findings

### 1. [blocker] Resolving a legacy answer can score that historical answer again

- **Where:** `pulsern/src/guest.js` · confidence high
- **Problem:** replayUnseen identifies baseline legacy occurrences with legacySignature, which includes key. Naming an unresolved row changes its key without creating a new answer, so replayUnseen treats the named historical row as an additional answer. When the same save also contains a new attempt, reconcileProgress installs this incorrectly replayed ability.
- **How it fails:** Start with one unresolved legacy miss already reflected in ability.n. Identify it through claimLegacyAt, then answer a question before the identity-change save is acknowledged, such as on a slow connection. Reconciliation replays both the renamed historical miss and the genuinely new answer. The saved log gains only one answer, but ability.n gains two and theta includes the old miss twice. An undated historical row also creates a rewards.days.undefined entry during replay.
- **Fix:** Match baseline legacy occurrences independently of editable identity/provenance fields, consuming each occurrence once. An identity correction must update an existing occurrence without invoking applyAnswer. Add a regression covering claimLegacyAt followed by a new live answer before the first save is acknowledged, asserting exact ability, XP, and day-ledger preservation.

### 2. [blocker] The legacy compatibility merge drops independently earned XP

- **Where:** `pulsern/supabase/migrations/022_progress_revision_guard.sql` · confidence high
- **Problem:** progress_merge_legacy_blob unions newly recorded answers but sets XP to greatest(stored XP, incoming XP). Independently earned XP is additive, not a high-water mark. The resulting blob can contain both devices' answers while permanently omitting one device's earnings.
- **How it fails:** Two tabs share a 40-XP baseline. The new client answers question A correctly and saves 50 XP. An already-open old client independently answers a different difficulty-1 question B correctly and submits its 50-XP snapshot without a revision. The trigger retains both answers but saves 50 XP instead of 60. The SQL tests currently assert maximum-value behavior rather than conservation of earnings.
- **Fix:** Apply newly merged answer/card earnings exactly once against authoritative saved progress instead of taking the larger total. If revision-less clients cannot supply enough information for an exact merge, require a client update rather than silently accepting a lossy approximation. Test two distinct earnings from the same baseline.

### 3. [blocker] Timestamp format takes precedence over when a flashcard was reviewed

- **Where:** `pulsern/supabase/migrations/022_progress_revision_guard.sql:46` · confidence high
- **Problem:** progress_review_stamp prefixes reviewedAt with "t" and legacy seen dates with "d", then compares the strings lexicographically. Consequently, any modern reviewedAt entry beats every legacy seen-only entry, even when the legacy review occurred on a later local day. guest.js reviewStamp/preferSchedule has the same ordering defect.
- **How it fails:** The new client grades a card Good on Monday, producing reviewedAt and a future due date. An already-open old client grades that card Again on Tuesday, producing seen: Tuesday without reviewedAt. Its save succeeds, but the trigger keeps Monday's Good schedule because "t..." sorts after "d...". The student's later failed retrieval is lost and the card does not return when it should. The existing later-legacy-grade SQL test gives the stored entry no reviewedAt, so it misses the production combination.
- **Fix:** Compare a common chronology rather than timestamp-type prefixes. Use the stored local review day to order different days, and precise timestamps only when comparable; use a conservative tie-break when timing is unknown. Fix both SQL and JavaScript comparators and test a modern stored grade against a later seen-only legacy grade.

### 4. [blocker] Legacy saves restore spent streak shields and prevent streak resets

- **Where:** `pulsern/supabase/migrations/022_progress_revision_guard.sql` · confidence high
- **Problem:** The compatibility merge constructs streak.count with greatest and streak.shield with boolean OR. Neither field is monotonic: the count must restart after an unprotected gap, and a shield must become false when consumed. These operations overwrite valid streak transitions.
- **How it fails:** The stored row has count 5, lastDay Monday, and shield true. An old tab studies Wednesday and correctly submits count 6 with shield false after bridging Tuesday. The trigger stores shield true again. Similarly, a legitimate restart to count 1 after a long absence retains the older larger count while adopting today's lastDay.
- **Fix:** Merge activity and replay the existing streak transition rules, or otherwise preserve the chronologically applicable streak state with explicit shield consumption. Do not use maximum/OR semantics for resettable or consumable state. Add SQL tests for both consuming a shield and restarting after an uncovered gap.

### 5. [blocker] Legacy calibrated answers are replayed using difficulty seeds

- **Where:** `pulsern/supabase/migrations/022_progress_revision_guard.sql:194` · confidence high
- **Problem:** The pre-change record function updates ability with the bank calibration but does not store rating on its answer rows. progress_apply_answer substitutes the difficulty seed whenever rating is missing, while progress_merge_legacy_blob ignores the incoming ability and installs that replay result. This changes the mathematical effect of genuine answers. replayUnseen in guest.js makes the same seed assumption for unseen unscoped legacy rows.
- **How it fails:** An old tab answers a difficulty-2 bank question calibrated at 1800, with category theta 1200 and n 0. Its correct answer should produce theta approximately 1238.774. On a revision-less merge, SQL substitutes rating 1300 and stores approximately 1225.603 instead. Subsequent readiness and adaptive selections use this incorrect ability.
- **Fix:** Require sufficient exact grading inputs for replay, such as the rating used or an authoritative ability delta. Do not present a seed-based reconstruction of a calibrated legacy answer as authoritative; provide a compatible transition or require those clients to update before further graded writes. Add an integration test using a legacy answer whose actual calibrated rating differs from its difficulty seed.
