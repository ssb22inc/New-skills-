## Assessment

Do not release yet. The save conflict handler can overwrite newer account progress, and guest import can award XP that the trial explicitly withheld. Multi-day trial streak summaries are also incorrect, and the screenshot fixture no longer supports the production save adapter. Findings are based on the supplied diffs and images; tests were not executed.

## Findings

### 1. [blocker] Conflict retry overwrites newer progress with a stale blob

- **Where:** `pulsern/src/App.jsx:401` · confidence high
- **Problem:** When the revision-checked update affects no row, store.set reads the current revision and retries the same unchanged payload against it. This defeats optimistic concurrency: the payload has not incorporated the progress associated with that newer revision.
- **How it fails:** Two tabs load revision 5. Tab A saves additional answers as revision 6. Tab B then saves its older snapshot, fails the revision-5 update, reads revision 6, and successfully replaces A's answers, XP, ability and schedules with B's stale blob. The new applyProgressWrite test does not exercise this production retry and therefore does not catch the loss.
- **Fix:** Do not retry an unchanged blob against a newly fetched revision. Surface the conflict and reload/reconcile server progress before saving again. Add a regression test against the actual store adapter with two independently loaded snapshots.

### 2. [blocker] Guest import drops the stem and awards previously withheld XP

- **Where:** `pulsern/src/guest.js:372` · confidence high
- **Problem:** builtinTrialQuestion discards both the authoritative question stem and the recorded word count. importTrialLive consequently constructs an empty stem, reducing every imported answer's reading-time floor to 2.5 seconds rather than the floor used during the trial.
- **How it fails:** Built-in question 1 has 23 stem words, so a correct answer at 2,600 ms earns zero XP during the trial because its floor is 2,880 ms. After signup, the empty-stem replay accepts those same 2,600 ms and awards 10 XP. The displayed saved XP and best run can therefore differ from the trial results. Existing tests use times below both floors or above both floors.
- **Fix:** Carry the actual stem from the trusted built-in catalog through import and pass it to applyAnswer. Test an answer time between 2,500 ms and the real question's floor, asserting that trial and imported XP and runs remain identical.

### 3. [blocker] Trial streak summaries are hard-coded to Day 1

- **Where:** `pulsern/src/guest.jsx:132` · confidence high
- **Problem:** SaveProgress displays "Day 1" in both streak summaries, and AuthScreen repeats that claim. Trials persist for seven days and retain each answer's local date; import correctly advances the account streak across those dates, so the displayed trial streak is not necessarily one.
- **How it fails:** A visitor answers part of the trial on Monday and finishes on Tuesday. The save and signup screens promise a Day 1 streak, but importing those answers produces a two-day streak. This contradicts the progress the code actually preserves.
- **Fix:** Derive the guest streak from its local answer dates using the same deterministic streak rules as import, and use that value in both SaveProgress and AuthScreen. Cover a trial spanning two local days.

### 4. [major] Screenshot fixture cannot execute the new progress save chain

- **Where:** `pulsern/ops/product-supabase-mock.js:13` · confidence high
- **Problem:** The new adapter calls insert(...).select("revision"), but this mock's insert returns a Promise containing only error:null. The preceding mocked update returns no revision, so an empty-account save necessarily reaches insert and throws because that Promise has no select method.
- **How it fails:** Regenerating product screenshots with the supplied empty-account fixture fails every initial autosave and renders the "Your latest answers aren't saved yet" alert instead of the documented normal new-account screen. The capture assertions only require other product text, so they can still accept this erroneous screen.
- **Fix:** Make insert and update return fluent, revision-aware query objects compatible with select and abortSignal, and return the appropriate revision on success. Have the capture reject unexpected save-error alerts.
