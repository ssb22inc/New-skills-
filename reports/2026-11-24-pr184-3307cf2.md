## Assessment

Not safe to ship. The change introduces a Stats-screen crash, review-schedule loss, incorrect trial-question resolution, and queued writes that can cross accounts. Two additional reward-feedback defects are reproducible from the code. Reviewed the supplied diff and images; tests were not executed.

## Findings

### 1. [blocker] Stats references a sign-out handler outside its scope

- **Where:** `pulsern/src/App.jsx:3052` · confidence high
- **Problem:** Stats renders onClick={signOutAndForgetTrial}, but that identifier is declared inside App and is neither passed to Stats nor defined at module scope. The imported helper is aliased to signOut. Evaluating the JSX therefore throws a ReferenceError when Stats renders.
- **How it fails:** A signed-in student opens Stats. The entire screen crashes before displaying performance, account settings, or sign-out. The new browser tests that navigate to Stats should fail on this path.
- **Fix:** Pass App's signOutAndForgetTrial handler into Stats as a prop and use that prop. Exercise the actual Stats render and sign-out action in a browser regression test.

### 2. [blocker] Adding trial answers erases existing missed-question schedules

- **Where:** `pulsern/src/App.jsx:590` · confidence high
- **Problem:** resolveGuestOffer passes a partial blob without missSchedule into mergeGuestIntoBlob. The merge consequently builds its schedule from an empty object, and the caller replaces the account's schedule with that result using setMissSchedule.
- **How it fails:** An existing account has corrected questions scheduled for future review and other misses with established intervals. The student selects Add to my account. All existing schedule entries disappear; only trial misses remain. Reloading can recreate current misses as due today, but cannot recover corrected questions' future reviews or their intervals.
- **Fix:** Include the current missSchedule in the merge input and preserve every unrelated schedule entry. Add a browser regression test with both a future corrected-question review and an existing missed-question schedule.

### 3. [blocker] Trial reviews resolve built-in IDs against the shared bank

- **Where:** `pulsern/src/question-review.js:62` · confidence high
- **Problem:** expandTrialQuestions resolves guest-<id> using the questions argument. App supplies allQuestions, which switches to the shared bank after a successful fetch. Shared-bank numeric IDs are not a reliable identity for bundled questions—the reason the handoff prefixes IDs in the first place.
- **How it fails:** A student misses built-in question 7 during the trial. After sign-in, bank item 7 is unrelated, or the original seeded item has been deleted/reinserted under another ID. Review Misses either serves the unrelated bank question as guest-7 or omits the trial miss entirely. Answering the unrelated item updates the original trial history and ability under the wrong content identity. The added test only supplies the built-in item, so it misses this production path.
- **Fix:** Resolve guest IDs from an explicit bundled-question registry, independently of the loaded bank. Test a bank containing a different question with the same numeric ID and a bank without that numeric ID.

### 4. [blocker] Queued progress writes can overwrite a different account

- **Where:** `pulsern/src/App.jsx:609` · confidence high
- **Problem:** Queued tasks retain an old account's payload, but store.set obtains whichever auth session exists when the task eventually executes. The queue is not invalidated on App unmount or account change.
- **How it fails:** Account A has a slow in-flight save and another snapshot queued behind it. A signs out and B signs in before the first request finishes. The old queue then executes store.set with A's payload, reads B's session, and upserts A's study history into B's progress row. This both corrupts B's progress and exposes A's history.
- **Fix:** Bind every queued write to the account that produced its payload, use that account ID for the row, and reject execution if the active account differs. Invalidate pending tasks on unmount/account change. Add a delayed-write test that switches accounts before releasing the first save.

### 5. [blocker] Revisiting case feedback falsely reports +30 XP

- **Where:** `pulsern/src/App.jsx:2617` · confidence high
- **Problem:** Case feedback uses the actual XP result only while justScored.current is true. Returning to an answered step sets that flag false and unconditionally falls back to '+30 XP', even when the new XP rules awarded zero or only five.
- **How it fails:** A student answers a case step too quickly and earns zero XP, or corrects a previously missed step for five XP. After moving forward and pressing Back, the same feedback claims '+30 XP' although the account total never received it.
- **Fix:** Store the XP result per case step, as QBank already does per question, and restore it with answered-step feedback. Do not substitute a fixed award when the actual result is unavailable.

### 6. [major] Fix-a-miss progress incorrectly depends on once-only XP eligibility

- **Where:** `pulsern/src/App.jsx` · confidence high
- **Problem:** record increments rewards.days[today].fixes only from res.fix. answerXp returns fix=false for every previously correct question, even when its latest answer was wrong. A learning-task completion is therefore incorrectly coupled to whether the question can still earn XP.
- **How it fails:** A student previously answered a question correctly, misses it during a later scheduled review, then corrects it today. If another miss remains open, Today's 'Fix a miss' task still shows incomplete despite the student having corrected one, contradicting the documented one-miss task.
- **Fix:** Determine miss correction from the question's latest pre-answer outcome, separately from once-only XP payment. Add a wrong-right-wrong-right regression test that verifies the final correction earns no additional XP but does complete the daily correction task.
