## Findings

### 1. [blocker] A revision conflict permanently strands unsaved answers

- **Where:** `pulsern/src/App.jsx:402` · confidence high
- **Problem:** When a conditional update finds no matching revision, the adapter throws "conflict" without rereading or reconciling progressRevision. Every subsequent autosave and "Try again" repeats the same obsolete revision. Pending answers exist only in memory, and reloading to obtain the current revision discards them.
- **How it fails:** Open the account in two tabs at revision N. After one tab saves revision N+1, the other tab cannot save any further answers. The same failure occurs if a write commits but its response is lost or aborted before the returned revision reaches the client. Retrying never recovers.
- **Fix:** Implement conflict recovery that preserves pending local work and reconciles it with freshly read server progress before retrying. Do not simply adopt the newest revision and overwrite the other device's blob. Test two clients sharing a backing row and a committed write whose response is lost.

### 2. [blocker] Reset races pending saves and can disable all subsequent persistence

- **Where:** `pulsern/src/App.jsx` · confidence high
- **Problem:** resetAll deletes the row and resets progressRevision without coordinating with saveQueue. An earlier write's delayed response can then assign its old revision in finish(), before finish checks whether that save is obsolete. The reset snapshot consequently updates a nonexistent row using a positive revision and never takes the insertion path.
- **How it fails:** A save updates the server row but its response is delayed. The student resets progress while that response is pending. Delete completes, progressRevision becomes 0, and the reset snapshot is queued. The old response then restores a positive progressRevision despite being stale. The queued reset and every later answer save fail with conflicts, so subsequent study is lost on reload.
- **Fix:** Serialize Reset with persistence: drain or safely invalidate pre-reset work before deleting, and prevent obsolete completions from changing the reset generation's revision. Add a browser regression test that delays a successful write response until after Reset completes, then verifies that a new answer persists.

### 3. [major] Blocked storage crashes the trial before its fallback can run

- **Where:** `pulsern/src/guest.jsx:21` · confidence high
- **Problem:** The storage helpers catch getItem/setItem failures, but window.localStorage and window.sessionStorage are evaluated outside those helpers' try blocks. Browsers or embedded contexts that deny access can throw from the property getter itself. initialGuest then crashes, rather than starting an in-memory trial; the save effect and leaveForAuth have the same problem.
- **How it fails:** A visitor opens /app/try with persistent storage disabled and a localStorage getter that throws SecurityError. GuestTrial fails during initialization, so the advertised no-account trial and the "could not store the trial" fallback are unreachable.
- **Fix:** Obtain both storage objects through guarded accessors and pass null when unavailable. Keep the in-memory trial usable and guard the handoff path as well. Test throwing storage property getters, not only stores whose setItem method throws.

### 4. [major] An open unresolved review never receives newly loaded candidates

- **Where:** `pulsern/src/App.jsx` · confidence high
- **Problem:** QBank stores the synthetic unresolved card, including its candidates array, in q when it is opened. Catalog changes rebuild reviewQuestions and the review pools, but the refresh effect handles only q.catalogMiss. An open q.unresolved therefore retains the incomplete candidate list from before the bank or case catalog finished loading.
- **How it fails:** Open an unresolved legacy miss while the bank request is pending. Initially only a bundled question or case step is available as a candidate. When the matching bank question arrives, it is still absent from the open chooser. The student must leave and reopen the sitting to see it, and can otherwise assign the saved miss to the wrong available source.
- **Fix:** Refresh the open unresolved card from the latest review pool when its catalogs change, retaining its legacy row identity. Keep incomplete catalog status explicit before accepting a source assignment. Test opening the chooser with a held catalog request, then releasing that request and verifying that the new candidate appears without restarting the sitting.
