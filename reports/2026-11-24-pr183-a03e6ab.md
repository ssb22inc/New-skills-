### 1. [blocker] Modal keyboard safety test cannot detect accidental answering

- **Where:** `pulsern/tests/browser/lab-fab-harness.jsx:22` · confidence high
- **Problem:** The fixture independently suppresses picks with `!open`, supplies no primary/check handler, and gives its Check answer button no answering action. Consequently, the browser test named "does not answer the question underneath an open toolkit" still passes if the shipped modal-shortcut guard is removed. Clear search also restores focus to an input, adding another unrelated reason shortcuts cannot fire.
- **How it fails:** Remove the `studySurfaceBlocked()` check from `useStudyKeys`. The test still reports success because its fixture refuses picks while open and cannot submit answers at all, leaving a critical accidental-answering regression undetected.
- **Fix:** Mount the shipped QBank with observable answer records, open the toolkit, deliberately move focus to the document, and send pick/submit shortcuts. Assert that selection and recorded scores remain unchanged. Verify that disabling the modal guard makes this test fail.

### 2. [major] Overlap calculation ignores the navigation's safe-area offset

- **Where:** `pulsern/src/question-nav.jsx:51` · confidence high
- **Problem:** `stickTop` subtracts only 62px, but the actual sticky row uses `bottom: calc(62px + env(safe-area-inset-bottom))`. On devices with a bottom inset, the row sits above the position checked by `navCoversCheck`, so the protection can incorrectly enable sticking over Check answer.
- **How it fails:** With an 844px viewport, a 120px navigation row, and a 34px bottom inset, the actual sticky row starts at 628px while the calculation checks from 662px. A Check answer button spanning 610–650px is considered clear, although the row overlays its bottom 22px.
- **Fix:** Calculate the sticky slot using the resolved CSS bottom offset, or share a measured offset with the CSS. Add a layout test with a nonzero safe-area offset and assert that Check answer remains unobscured.
