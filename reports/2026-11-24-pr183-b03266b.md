## Findings

### 1. [major] Text-only question changes do not trigger collision avoidance

- **Where:** `pulsern/src/lab-fab.jsx:118` · confidence high
- **Problem:** The MutationObserver watches child-list changes and selected attributes, but not characterData or element resizing. React can replace a question's stem and option text by updating existing text nodes without producing any observed mutation. settleKey is only the app tab, so that does not trigger repositioning either.
- **How it fails:** On a phone at scroll position zero, skip a short multiple-choice question for another multiple-choice question with longer text and the same option count. If the floating button occupied empty space beside or below the short question, the longer stem or options can move underneath it. The scrollTo(0, 0) call need not produce a scroll event, leaving the button covering content until another qualifying interaction occurs. The browser harness never changes the underlying question, so its collision tests miss this path.
- **Fix:** Observe characterData changes and layout resizing, or explicitly trigger settling when the displayed question/card/step changes. Add a browser test that switches between differently sized questions without scrolling and checks the settled button against the new reading surfaces and controls.

### 2. [major] New ARIA radios have no arrow-key behavior

- **Where:** `pulsern/src/study-keys.js:29` · confidence high
- **Problem:** The shortcut handler rejects events from radios and checkboxes on the assumption that those controls handle their own keyboard navigation. However, the new question choices and matrix cells are buttons with role="radio", not native radio inputs, and no radio-group keyboard handler is implemented. Adding an ARIA role does not supply native radio behavior.
- **How it fails:** Tab to a case-study answer or a matrix radio and press an arrow key: it neither moves/selects within the answer group nor performs the advertised study navigation. Clicking a choice also leaves focus on a custom radio where the advertised digit shortcuts are ignored. The new unit test only asserts that the shortcut handler returns null; it does not verify that the supposed replacement behavior exists.
- **Fix:** Use native, correctly grouped radio inputs or implement grouped radio keyboard behavior with arrow-key selection and managed tab stops. Keep shortcut exclusions aligned with that implementation, and exercise the focused controls in a browser test rather than testing only event rejection.
