## Assessment

Request changes: the worker can lose queued work during a storage failure, and the API can report that audio is being prepared when no repair work was queued. This was a static review; tests were not run, and the unchanged narration normalizer was not supplied for independent verification.

## Findings

### 1. [blocker] Retain the original job if persisting its replacement fails

- **Where:** `pulsern/ops/read-aloud-worker.mjs:128` · confidence high
- **Problem:** After the final transient attempt, if saveRejected fails, the worker writes a give-up entry to the retry lane but ignores that upload's result. It then removes the original fresh-queue entry even if the retry upload also failed. This loses the pending job and its retry history without saving a terminal record.
- **How it fails:** A fresh job reaches its fifth attempt while the provider is failing. Storage is full, so both the rejection-record upload and retry-entry upload fail, but deletion remains available. The original queue entry is deleted, leaving neither a queued job nor a rejection record.
- **Fix:** Check the retry upload result and remove the original only after the replacement is durably saved. If neither record nor replacement can be saved, retain the original and fail the run. Add a regression test where both uploads fail while removal succeeds.

### 2. [major] Do not report preparation after an unrepairable cached-audio failure

- **Where:** `pulsern/api/_speak.js:495` · confidence high
- **Problem:** When a passing record exists but creating its signed audio URL fails, speak falls through to queue admission. The queue loop then skips that passage because readRecord still returns the passing record, and the route returns 202 despite queuing no work for it. Prewarming also skips the same record, so a missing audio object is never rebuilt.
- **How it fails:** A passage retains its passing JSON record but its MP3 is missing. Every Listen request returns 'being prepared'; no queue entry is created, and the scheduled worker continually regards the passage as already decided. A transient signing-service error also incorrectly reports preparation instead of service unavailability.
- **Fix:** Distinguish signing-service errors from missing audio. Return an unavailable response for operational signing failures. For a missing object, invalidate or repair the cached record and ensure the worker actually regenerates the audio rather than skipping it. Test both cases with an existing passing record.
