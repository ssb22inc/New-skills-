## Assessment

Do not ship. The new reconciliation path corrupts persisted XP and reward history, can award XP that the guest trial rejected, and can reverse the order of delayed answers. The supplied tests do not cover these failing persistence scenarios. Review was based on the supplied diff and images; tests were not run.

## Findings

### 1. [blocker] Saving an undo restores the XP it should remove

- **Where:** `pulsern/src/guest.js:238` · confidence high
- **Problem:** When there are no unseen question attempts, reconcileProgress takes the maximum of server and local XP. This prevents legitimate XP reductions, including Flashcards' Undo grade. The returned reconciled blob is applied back to the screen, restoring the removed XP while leaving the card schedule undone.
- **How it fails:** Grade a card Good, wait for its +5 XP save to succeed, then return to that card and choose Undo grade. The local handler subtracts 5, but blobForSave raises XP back to the accepted value. Regrading the card can then award another 5 XP.
- **Fix:** Reconcile XP changes against the shared baseline rather than treating XP as monotonically increasing. Preserve explicit grade reversals and add an integration test that waits for the Good save, performs Undo through the real App/store path, and verifies the saved and displayed XP.

### 2. [blocker] Question replay discards flashcard rewards during reconciliation

- **Where:** `pulsern/src/guest.js:243` · confidence high
- **Problem:** If either side has an unseen question attempt, reconciliation replaces XP, rewards, daily and streak with a replay starting from the baseline. That replay contains only question attempts; flashcard grades and other non-question changes made since the baseline disappear. Merging srsMap separately does not preserve their XP or daily ledger.
- **How it fails:** Two devices load the same baseline. Device A grades a flashcard Good and saves +5 XP and one reviewed card. Device B answers a new question for +10 XP, encounters the revision conflict, and reconciles against A's save. The resulting blob retains the flashcard schedule but stores only 10 XP and zero reviewed cards instead of 15 XP and one card.
- **Fix:** Merge non-question progress independently of question replay, using baseline-aware deltas or identifiable grade/undo events. Preserve reward preferences, cover grants and celebration markers as well. Test a revision conflict combining a flashcard grade on one device with a question answer on the other.

### 3. [blocker] Imported trial answers lose the reading-time evidence needed when saving

- **Where:** `pulsern/src/guest.js:568` · confidence high
- **Problem:** importTrialLive supplies the catalog stem to applyAnswer but does not supply words, so the imported log row retains neither the stem nor its word count. If an existing empty account row is the save baseline, blobForSave replays these new attempts. replayUnseen substitutes an empty stem, lowering the reading-time floor to 2.5 seconds and potentially awarding XP that both the guest trial and import correctly rejected.
- **How it fails:** Answer built-in question 1 correctly in 2,600 ms: its 23-word stem requires 2,880 ms, so the trial earns zero XP. Sign into an older account with a saved row and an empty log. Import initially earns zero, but saving replays the row with an empty stem and awards 10 XP. The handoff confirmation still reports the original zero-XP summary.
- **Fix:** Preserve the authoritative catalog word count and rating on every imported answer passed to applyAnswer, or persist enough authoritative scoring evidence that reconciliation cannot change the original decision. Test this through blobForSave using an existing empty-account baseline and a duration between 2.5 seconds and the catalog item's actual floor.

### 4. [blocker] Delayed answers are appended after newer answers and replayed backwards

- **Where:** `pulsern/src/guest.js:166` · confidence high
- **Problem:** mergeLogs always emits server rows first and appends unmatched local attempts afterward, without considering when they occurred. reconcileProgress then uses this order for Elo updates, repeat/fix XP, streak advancement and review scheduling. Review Misses also treats the last array entry as the latest result.
- **How it fails:** Device A answers question 7 incorrectly on Tuesday while its saves fail. Device B answers question 7 correctly on Wednesday and saves. When A retries, reconciliation orders Wednesday's correct answer before Tuesday's miss. The persisted latest result becomes incorrect, its schedule is reset from Tuesday, and a Monday baseline streak can consume a shield instead of counting Tuesday and Wednesday consecutively.
- **Fix:** Record stable answer-time metadata and merge new attempts in chronological/causal order before storing the log and replaying dependent calculations. Preserve the legacy ordered prefix. Add a regression test where an older offline miss arrives after a newer saved correction and verify the latest result, review date, XP, ability and streak.
