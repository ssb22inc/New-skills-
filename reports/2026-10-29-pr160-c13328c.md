## Findings

### 1. [blocker] The fifteen-minute preparation message is shown when preparation cannot run again today

- **Where:** `pulsern/src/read-aloud.jsx:285` · confidence medium
- **Problem:** Every 202 response produces a message saying the voice is usually ready within 15 minutes. Queue admission does not check the remaining synthesis budget, and prewarming consumes that budget independently of admission. The UI therefore presents the short turnaround even when the system is deliberately unable to synthesize anything until the next Eastern calendar day.
- **How it fails:** While the bank is being prewarmed, the worker exhausts the 4,000-synthesis daily cap. A student then requests an unvoiced item. Admission still succeeds and returns 202, so the app displays the fifteen-minute message, although every subsequent worker run must stop at the budget cap, potentially for many hours.
- **Fix:** Remove the unsupported turnaround estimate or return budget-aware preparation status and display that work is waiting for the next budget day. Test the displayed message for an admitted request made after the synthesis budget is exhausted.

### 2. [major] Queue deletion errors are ignored and can starve later requests

- **Where:** `pulsern/ops/read-aloud-worker.mjs:163` · confidence high
- **Problem:** The worker ignores Supabase's returned error when removing completed queue entries. The already-decided and rejection paths do the same. Consequently, deletion failures are reported as successful processing rather than operational failures.
- **How it fails:** Uploads and downloads work, but remove returns an error. Completed entries remain queued, and the workflow stays green. Once 420 old, decided entries accumulate with the default max of 200, listLane repeatedly selects only those entries. Their deletion keeps failing, newer requests are never reached, and prewarming also skips those newer passages because they remain queued.
- **Fix:** Check removal results throughout drainQueue and mark deletion failures as operational failures. Ensure undeletable decided entries cannot indefinitely hide later pending work. Add tests where remove returns an error, asserting a failed run and preservation of progress for later requests.

### 3. [major] Concurrent live requests synthesize the same passage multiple times

- **Where:** `pulsern/api/_speak.js:535` · confidence high
- **Problem:** The live path checks for a saved record and then synthesizes without acquiring a passage-level claim. The numbered budget slots cap total spending but do not deduplicate purchases. The paid-once test exercises only sequential requests.
- **How it fails:** With OPENAI_API_KEY configured on the web server, two students request the same uncached passage concurrently. Both observe no record, reserve separate spending slots, and purchase synthesis and transcription for identical text. Common passages such as "Choose one answer." make this particularly plausible. Duplicate purchases consume the daily budget and can deny other students voice preparation unnecessarily.
- **Fix:** Acquire a shared, leased claim keyed by speechKey before synthesis, recheck the saved record after acquiring it, and coordinate with scheduled synthesis as well. Add a concurrent-request test proving that identical passages produce one paid synthesis while both callers can obtain the checked result.
