## Findings

### 1. [blocker] Consecutive record calls overwrite answers from the same render

- **Where:** `pulsern/src/App.jsx:964` · confidence medium
- **Problem:** record reads log, xp, ability, daily, and missSchedule from its render snapshot, then replaces those states directly. Two calls before React commits both calculate from the same starting values, so the second drops the first answer and its XP/ability update. Meanwhile, rewardsRef and runRef advance immediately, leaving counters inconsistent with the saved answer history. The previous functional log and XP setters did not lose updates this way.
- **How it fails:** Starting with an empty log, deliver two scored answers in one render turn, as can happen when recording a completed exam's results. The saved log contains only the second answer. I could not verify whether the unchanged ExamCenter currently forces a React commit between every callback because its implementation was not supplied.
- **Fix:** Apply answers through one reducer or a synchronously maintained complete progress snapshot, rather than combining render-state snapshots with a few mutable refs. Add a mounted-App regression that records multiple answers before a render and verifies every log row, XP increment, ability update, and schedule survives; sequential applyAnswer unit tests do not cover this failure.

### 2. [blocker] Historical replay discards ability contributed by unclassified history

- **Where:** `pulsern/src/answer-apply.js:35` · confidence high
- **Problem:** canReplay explicitly accepts unclassified rows, but replayAbility resets all categories to baseline and skips those rows. Consequently, an import inserted behind an existing answer can erase valid contributions already present in persisted ability. Readiness then uses the reduced ability while its evidence count still includes the entire log.
- **How it fails:** An existing account has legacy answers that classifyLog marks unclassified, plus a newer timestamped answer. The student imports an earlier trial from another browser or accepts a previously deferred trial offer. insertedBehind is true, canReplay returns true, and replay resets the legacy answers' category theta/n instead of preserving them.
- **Fix:** Do not replay unless every contributing historical answer can actually be reconstructed. At minimum, unclassified rows must prevent full replay. Preserve an authoritative baseline for unreconstructable history if chronological insertion must be supported. Add a regression with non-baseline persisted ability, an unclassified legacy row, and an older imported answer.

### 3. [blocker] Raw schedule adoption transfers review history between different sources

- **Where:** `pulsern/src/answer-apply.js:50` · confidence high
- **Problem:** adoptRawSchedule assumes that schedule[q.id] belongs to the current canonical question without checking its source or catalog ownership. rekeySchedule also leaves the numeric entry behind after copying it to a canonical key. Together, these allow a bank question's missed-review ladder to be adopted by an unrelated built-in question with the same number.
- **How it fails:** Legacy bank question 7 has a scheduled miss. Classification produces bank:7 while retaining schedule[7]. Importing a correct trial answer for builtin:7 adopts that remaining numeric entry and advances it, scheduling a built-in question that was never missed. If adoption happens before classification, it can also remove the numeric date before the bank history is rekeyed.
- **Fix:** Adopt a numeric schedule only when catalog evidence establishes that it belongs to the same canonical identity. Remove the obsolete numeric entry after a confirmed rekey, and retain ambiguous entries separately rather than assigning them to whichever source answers next. Test bank:7 and builtin:7 together with a legacy numeric schedule.

### 4. [major] Ambiguous legacy identities silently remove existing misses from review

- **Where:** `pulsern/src/question-key.js:72` · confidence high
- **Problem:** When an old numeric ID occurs in both catalogs, classifyLog persists unclassified:true. latestResults and unscopedRows then ignore that answer, while scheduleEntry explicitly rejects its numeric review date. A previously available missed question therefore disappears from both Review Misses and the due Today pool and is instead treated as unseen.
- **How it fails:** A saved account has a wrong answer and due schedule under ID 7. Both the bundled registry and loaded bank contain ID 7. After catalog classification, Review Misses no longer offers that miss even though the wrong answer and review date still exist in the saved blob. The new tests assert this exclusion rather than detecting the feature regression.
- **Fix:** Preserve unresolved misses as a visible, actionable review state instead of silently dropping them. Resolve identical seeded content where catalog evidence permits; otherwise provide an explicit reconciliation path and do not treat unresolved history as new or the review pool as cleared. Add a migration test that verifies an existing miss remains accessible after an ID collision.
