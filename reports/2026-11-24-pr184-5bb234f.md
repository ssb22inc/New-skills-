## Assessment

Two defects remain in the guest-trial flow. The warfarin correction is appropriate. Review was based on the supplied code and images; tests were not executed.

## Findings

### 1. [major] The question navigation's Labs button does nothing for guests

- **Where:** `pulsern/src/guest.jsx:84` · confidence high
- **Problem:** QBank renders QuestionNav, whose Labs control dispatches OPEN_LABS_EVENT. Only App subscribes to that event; GuestTrial renders QBank without App and never installs an equivalent listener. Its toolkit can therefore open through the floating button, but not through the question navigation.
- **How it fails:** An anonymous student opens /app/try and taps Labs in the question navigation. Nothing opens. The guest browser tests miss this because they open the toolkit exclusively through .lab-fab.
- **Fix:** Subscribe to OPEN_LABS_EVENT in GuestTrial, select the labs section, open the toolkit, and remove the listener on unmount. Add a browser test that opens it through the question-navigation control.

### 2. [major] Legacy signup query prevents a partially completed trial from reopening

- **Where:** `pulsern/src/app-routing.js:26` · confidence high
- **Problem:** authModeFromUrl checks start=1 before APP_TRY. AuthGate's onTry handler preserves the current query string, so entering the trial from the supported /app/?start=1 signup URL produces /app/try?start=1, which is subsequently classified as signup rather than try.
- **How it fails:** A visitor arrives at /app/?start=1, chooses Try questions first, answers one question, and reloads. They land on signup instead of resuming the trial. Because AuthScreen hides the Try button when saved trial answers exist, there is no visible way to finish the remaining questions.
- **Fix:** Give the explicit APP_TRY pathname precedence over the legacy start=1 fallback, or remove that mode-selection parameter when navigating into the trial. Test reloading a partially completed trial entered from /app/?start=1 through the real AuthGate.
