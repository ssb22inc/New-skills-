## Assessment

Request changes. The patch introduces answer loss after reload, plaintext account-history retention after sign-out, incorrect recovery calculations, and defects in legacy-review and guest-reward handling. The added tests do not exercise these failing paths. Review was limited to the supplied changes; tests were not executed.

## Findings

### 1. [blocker] Live attempt IDs collide after every app remount

- **Where:** `pulsern/src/answer-apply.js:49` · confidence high
- **Problem:** App.record generates attempts as live:<accountId>:<counter>, but liveAttempt starts at zero on every mount. Previously saved answers retain those same attempt IDs. applyAnswer therefore rejects genuine new answers as duplicates. App.record then dereferences the null result at res.xp, throwing before QBank can finish submitting the answer.
- **How it fails:** Answer one signed-in practice question, let it save, then reload. The next answer receives live:<same-account>:1, matches the saved first answer, and is discarded. Checking the answer throws instead of recording it. Readiness-exam recording uses this same path.
- **Fix:** Generate globally unique attempt IDs, such as a per-session UUID plus a counter, while retaining a stable ID for retries of the same submission. Add a full-App regression that loads saved live attempts, records another answer after remount, and verifies its log, ability, XP, and feedback.

### 2. [blocker] Sign-out leaves identifiable answer history in plaintext localStorage

- **Where:** `pulsern/src/progress-load.js:136` · confidence high
- **Problem:** The timeout recovery journal persists answer IDs, outcomes, categories, dates, and attempts after sign-out. Hashing the storage key does not protect the payload: real live attempt strings contain the raw account UUID as live:<userId>:<counter>. signOutAndForgetTrial deliberately leaves this journal behind. The test uses artificial attempt names and only excludes the quoted string "u1", so it misses the actual identifier embedded inside an attempt.
- **How it fails:** On a shared computer, a progress write hangs and the student signs out. After three seconds, their unsaved account-linked study history is written to localStorage. The next person can inspect it without signing into that account. Expiration is only checked when the original account's journal is read, so an abandoned journal can remain beyond seven days.
- **Fix:** Do not retain plaintext account history after sign-out. Use recovery encrypted with a key unavailable while signed out, or offer an explicit download/discard decision. Test the actual App-produced attempt format and verify that signed-out device storage exposes neither account identifiers nor answer history.

### 3. [blocker] Recovered answers use different XP and ability calculations

- **Where:** `pulsern/src/progress-load.js:119` · confidence high
- **Problem:** applyUnsavedAnswers reconstructs a question without its stem, lowering minThinkMs to 2.5 seconds. It also lacks the item's effective calibrated rating. App.loadProgress passes calibration from its initial empty-object closure, so restored bank answers use difficulty seeds rather than their original calibration. Recovery consequently changes the answer's XP and Elo effect.
- **How it fails:** A long diff-2 bank question is calibrated at 1800 and answered correctly in four seconds. Live scoring awards no XP because its reading floor is six seconds and updates ability using 1800. If its save times out and the journal is restored, recovery awards 20 XP and updates ability using the 1300 seed. The recovered readiness state differs from the original answer.
- **Fix:** Retain the bounded metadata needed to reproduce answer semantics, including the effective item rating, reading-time threshold, and scheduling policy, and use it during replay. Add recovery tests with a non-seed calibrated rating and an answer between 2.5 seconds and the original reading floor.

### 4. [major] Ambiguous legacy misses lose their built-in candidate

- **Where:** `pulsern/src/question-review.js:161` · confidence high
- **Problem:** Once the bank loads, the active question list excludes bundled questions. classifyLog marks a legacy numeric miss unclassified when both catalogs contain that number in the same category. expandTrialQuestions does not restore the bundled candidate for such a row because its identity falls back to the bare number, which matches neither builtin: nor guest-. unresolvedCards then builds candidates only from the active list.
- **How it fails:** A legacy save contains a miss on built-in question 3, and the approved bank also contains a Pharmacology question 3. After catalog classification, Review Misses asks which question it was but offers only bank:3. The student cannot select the actual built-in question, so the original miss cannot be correctly restored.
- **Fix:** Build unresolved-review candidates from the complete source catalogs, including bundled questions, independently of the active fresh-question pool. Add a regression covering a legacy built-in miss after a same-number, same-category bank item loads.

### 5. [major] Resolving a legacy miss strands the Today round on its loading screen

- **Where:** `pulsern/src/App.jsx` · confidence high
- **Problem:** The q.unresolved choose handler calls endSession(), which changes phase to pick. In an automatic QBank, the startup effect depends only on auto, so it does not run again when phase returns to pick. The component then renders 'Loading a question…' indefinitely.
- **How it fails:** Start Today's round with a due unresolved legacy miss. Select one of its identity candidates. The log is resolved, but the automatic round neither serves another question nor calls onDone; it remains on the loading screen until the student leaves the round.
- **Fix:** Resume automatic selection after identity resolution using the updated log and schedule, rather than returning to a pick state that has no active transition. Add a browser test that resolves a legacy miss inside Today and successfully continues the round.

### 6. [major] Existing accounts can repeatedly earn trial XP for the same questions

- **Where:** `pulsern/src/guest.js:371` · confidence high
- **Problem:** importTrialOntoHistory awards XP without adding the trial questions to the log or retaining their canonical identities as already rewarded. It remembers only attempt IDs. A later trial has new attempt IDs, and the known set still contains only the account log, so the same built-in questions qualify for first-answer XP again.
- **How it fails:** An account with existing history adds a considered, correct trial answer for builtin:1 and earns XP. Sign out, complete another trial containing that question, sign back in, and add it again. Because neither import records builtin:1 as known, both imports pay first-answer XP, contrary to the once-per-question rule.
- **Fix:** Persist canonical trial reward receipts or outcomes separately from the readiness log, and consult them during imports and subsequent XP decisions. Preserve the documented unchanged-readiness behavior. Test two different trial attempt IDs for the same question on an existing account and require the second import to award zero XP.
