## Assessment

Do not release yet. Progress reconciliation can corrupt ability, review schedules, and streak credit. The guest handoff also loses access to retained answers when browser storage getters throw. These findings are based on the supplied diffs and images; tests were not executed.

## Findings

### 1. [blocker] An older incoming attempt is scored after newer baseline answers

- **Where:** `pulsern/src/guest.js:424` · confidence high
- **Problem:** replayUnseen starts with the baseline's already-updated ability and schedule, then applies incoming attempts while skipping every baseline attempt. Sorting the merged log does not fix this: an incoming attempt inserted before a baseline answer is still scored after it. reconcileProgress then installs this incorrectly ordered ability and schedule.
- **How it fails:** Two devices start from the same progress. Device B answers a question incorrectly while offline. Device A subsequently answers it correctly and saves, establishing A's baseline. B reconnects and merges both answers chronologically, correctly leaving the question on the corrected-miss ladder. When A next saves a setting, its conflict reconciliation applies B's older miss on top of A's newer correct answer. The log still ends in a correct answer, but ability reflects the reverse order and the review schedule is reset to tomorrow instead of retaining the corrected-miss interval.
- **Fix:** Recompute the affected answer suffix from a checkpoint preceding the earliest incoming attempt, or process ordered answer events transactionally on the server. Do not apply an older attempt to a baseline that already includes later answers. Add a two-device regression with an acknowledged newer answer followed by a delayed older miss.

### 2. [blocker] Question-only replay overwrites flashcard streak and daily credit

- **Where:** `pulsern/src/guest.js:493` · confidence high
- **Problem:** Whenever there is an unseen question attempt, reconciliation replaces daily and streak with replayed.daily and replayed.streak. That replay includes question answers only. Flashcard grades update these fields through touchDay, but their activity is never replayed, even though card operations and reward-day entries are retained elsewhere.
- **How it fails:** The saved baseline has a five-day streak last touched November 22. While saves are failing, the student grades a card on November 23 and answers a question on November 24. Live state correctly reaches day seven with the shield ready. Saving reconciles from the November 22 baseline using only the November 24 question, producing day six and consuming the shield for a supposedly missed November 23. Even without crossing midnight, a pending card grade followed by a question loses the card's increment from daily.answered.
- **Fix:** Include flashcard grade/undo activity when reconstructing daily activity and streaks, rather than replacing those fields with question-only replay results. Add a regression covering an unsaved card-only day followed by a question on the next local day.

### 3. [blocker] Throwing storage getters prevent the retained trial from importing

- **Where:** `pulsern/src/App.jsx:734` · confidence high
- **Problem:** Both window.localStorage and window.sessionStorage are evaluated before readGuestForHandoff runs. If either getter throws, the catch leaves guest null, so the function never checks the in-memory held trial or any accessible storage adapter. This defeats the fallback deliberately provided by holdGuestTrial.
- **How it fails:** A browser denies storage access. The guest completes questions and sees the instruction to create an account before leaving the tab. leaveForAuth retains the answers in memory, and the student signs into an empty account in that same tab. App skips the handoff because a storage getter throws, saves an empty account, and shows no import confirmation. Signing out subsequently clears the retained answers.
- **Fix:** Obtain each storage adapter independently with storageOrNull and always call readGuestForHandoff, including when both adapters are null so its in-memory fallback can run. Guard the post-save storage cleanup similarly. Add an integration test that denies storage getters and completes the same-tab handoff.
