## Findings

### 1. [blocker] Imported clinical data can change without invalidating the visual-review cache

- **Where:** `pulsern/ops/review-diagrams-lib.mjs:257` · confidence high
- **Problem:** diagramSources follows import-from statements only into JS/JSX/MJS files. Imported JSON and re-exported dependencies are omitted from the request and reviewKey. Meanwhile, sourceKey does hash top-level diagram JSON. This allows the review job to detect a source change but then reuse an approval whose reviewer never saw that change.
- **How it fails:** A diagram imports a JSON threshold used only for non-example patient values. Changing that threshold leaves its example screenshots, static claims, and collected source text unchanged. The reviewKey therefore remains unchanged, canReuse returns true, and review-diagrams.mjs updates the old PASS to the new sourceKey without calling Astra. The mapper can then publish the changed interpretation as currently approved.
- **Fix:** Build the review request and approval hashes from a complete, consistent dependency graph, including imported data and re-exports. Fail closed on dependencies that cannot be represented. Add a regression test that changes an imported JSON value used outside the example and proves both that the request includes it and that the previous PASS cannot be reused.

### 2. [blocker] Unreviewed feature-branch code receives the production service-role key

- **Where:** `.github/workflows/pulsern-narrate.yml:96` · confidence medium
- **Problem:** The workflow checks out inputs.branch, installs its dependencies, and executes its ops/narrate.mjs with SUPABASE_SERVICE_ROLE_KEY. The branch guard validates the ref's spelling and existence, not its approval. With the repository-secret configuration documented here, a repository writer who can dispatch workflows can run their own code with the production database credential. Requesting Astra review afterward does not protect this execution.
- **How it fails:** A writer pushes a feature branch whose narrate.mjs sends the service-role key to an external endpoint or directly changes approved content in Supabase, then dispatches this workflow for that branch. Those operations happen before any review of the resulting commit and do not require merging the branch. I could not verify whether external organization controls further restrict dispatch access.
- **Fix:** Keep production credentials in a protected environment and ensure the credential-bearing job executes only trusted, reviewed code—not scripts or dependencies from the selected feature branch. Treat branch content as data, or separate untrusted rendering/build work from a trusted credential-bearing publication job with enforced approval of the exact inputs.

### 3. [major] A failed git add can produce a successful partial save

- **Where:** `pulsern/ops/save-results.sh:24` · confidence high
- **Problem:** The script does not enable errexit and ignores each git add exit status. The later patch-id check proves only that whatever was committed reached the branch; it does not prove that all requested results were staged.
- **How it fails:** The item-map path stages successfully, but an existing reports path is git-ignored or otherwise fails to stage. The script commits and pushes the map alone, emits pushed=true, and exits successfully while the paid report remains uncommitted. If every add fails and the index is empty, it instead reports 'Nothing new to save' with exit 0. The current tests cover missing paths and push failures, but not staging failures.
- **Fix:** Explicitly fail on every unsuccessful git add for an existing requested path. Preserve the intentional handling of paths never created by an early-stopped run. Add tests with a changed tracked result plus an existing ignored result path, and with only a failing staging operation; neither may report success.
