## Assessment

Request changes. Provider authentication failures can permanently disable read-aloud passages, the paid worker does not honor the documented configurable spending cap, and live synthesis uses a separate spending counter. Prewarming outages can also leave the workflow green. Review is based on the supplied diffs; I could not run the tests or inspect the imported narration QA implementation.

## Findings

### 1. [major] Provider authentication failures permanently reject otherwise valid passages

- **Where:** `pulsern/api/_speak.js:278` · confidence high
- **Problem:** The error classification treats almost every 4xx response as a permanent refusal of the passage. That includes 401 and 403 authentication or project-permission failures, and 404 model/endpoint configuration failures. Both execution paths save a terminal rejection record for these errors. Those records are subsequently reused indefinitely under the current QA version.
- **How it fails:** The OpenAI key is revoked or temporarily misconfigured. Each prewarming run marks up to its run limit of valid passages as unvoiceable. Restoring the key does not recover those passages: readRecord finds pass=false, the route returns 422, and prewarming skips them.
- **Fix:** Only persist a terminal rejection for an explicitly identified passage-specific refusal. Treat authentication, permission, model configuration and other service-wide failures as run failures without creating rejection records. Add recovery tests showing that a passage remains eligible after a 401 or 403 and succeeds once credentials are corrected.

### 2. [major] The documented global spending override never reaches the paid worker

- **Where:** `pulsern/ops/read-aloud-worker.mjs:241` · confidence high
- **Problem:** The CLI calls drainQueue and prewarmBank without supplying limits, so both always use LIMITS.global=4000. SPEAK_GLOBAL_DAILY is read only by the Vercel route, while the worker independently synthesizes the bank ahead of demand. Lowering the documented Vercel cap therefore does not lower the worker's paid synthesis cap.
- **How it fails:** The owner sets SPEAK_GLOBAL_DAILY=100 to reduce daily spend. New student admissions are capped at 100, but the scheduled worker continues prewarming and can make 4,000 paid syntheses that day even with no student requests.
- **Fix:** Give the route and worker an authoritative shared spending-limit configuration, or explicitly propagate a worker setting through the workflow and correct the setup instructions. Test the production worker configuration path with a non-default cap, rather than only passing custom limits directly into imported functions.

### 3. [major] Live synthesis and scheduled synthesis do not share the app-wide spending counter

- **Where:** `pulsern/api/_speak.js:347` · confidence high
- **Problem:** The live route's beforeTake callback claims usage/<day>/all through reserve, whereas the worker claims usage/<day>/spend through reserveSpend. When OPENAI_API_KEY is present on the server—a supported execution path—each path can independently exhaust a full global allowance.
- **How it fails:** The scheduled worker spends 4,000 synthesis slots prewarming the bank. Signed-in students can still cause another 4,000 live syntheses that day because the route checks the separate all counter. The stated app-wide synthesis ceiling is exceeded.
- **Fix:** Require both execution paths to claim the same paid-spend counter immediately before every synthesis. Keep queue-admission and per-student accounting separate as needed. Add a mixed worker/live-route test proving their combined synthesis count cannot exceed one global limit.

### 4. [major] Prewarming provider and storage failures still produce successful workflow runs

- **Where:** `pulsern/ops/read-aloud-worker.mjs:261` · confidence high
- **Problem:** prewarmBank reports synthesis/transcription outages and failed audio saves through stopped values beginning with "provider:". The CLI failure condition checks only "bank:" and "cursor:" values, so these failures exit successfully. Unexpected exceptions caught around prewarmBank are likewise generally converted into successful runs. This contradicts the documented promise that provider outages or storage trouble fail the job.
- **How it fails:** With an empty student queue, OpenAI returns 503 during bank prewarming. Prewarming stops immediately, q.providerDown remains false, pruning succeeds, and the workflow exits zero. Repeated scheduled runs remain green while no bank audio is produced. A failed storage write during prewarming follows the same path.
- **Fix:** Represent operational failure separately from normal stops such as max, budget and skipped, and make every provider/storage operational failure produce a nonzero CLI exit. Add tests for the CLI exit decision with an empty queue and failing prewarming provider or storage.
