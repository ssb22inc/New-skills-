## Assessment

Do not ship. Two persistence defects can permanently stop progress saves during ordinary use. The supplied tests do not exercise either failing sequence.

## Findings

### 1. [blocker] A superseded save can commit without advancing the local revision

- **Where:** `pulsern/src/App.jsx:389` · confidence high
- **Problem:** createSaveQueue makes isCurrent() false as soon as a newer snapshot is queued, but it does not cancel the active request at that point. If that request successfully updates the database, finish() throws at the post-request current() check before recording the returned revision. Subsequent saves use the obsolete progressRevision, fail their revision filter, and report a conflict. The retry button submits the same obsolete revision, so saving cannot recover within the session.
- **How it fails:** A student answers a question while a previous autosave is in flight, or earns a badge that triggers another rewards save. The first database update commits after the newer snapshot is queued. Its revision response is discarded as stale, and the newer answer and all subsequent work remain unsaved even after tapping Try again.
- **Fix:** Keep revision tracking scoped to the account and let an already-issued serialized write finish and advance that revision even when a newer payload is waiting. Supersession should skip queued snapshots, not discard acknowledgements of committed writes. Add recovery for ambiguous completions/conflicts and a test that queues another save after the first request starts but before its successful response arrives.

### 2. [blocker] Reset deletes the row but leaves the revision unable to recreate it

- **Where:** `pulsern/src/App.jsx:395` · confidence high
- **Problem:** resetAll() deletes the progress row without resetting progressRevision. After any successful autosave, that revision is nonzero. The reset snapshot therefore updates a nonexistent row, and this insert fallback is skipped because progressRevision !== 0. Every subsequent save conflicts until the app is reloaded. The browser test named "Reset still works" only checks that delete was called; it never checks that post-reset progress can be saved.
- **How it fails:** A signed-in student loads normally, chooses Reset all progress, and starts studying again without reloading. The old row is deleted, but none of the new answers, XP, or schedules can be persisted. Retrying does not help, and leaving the page loses the new work.
- **Fix:** Coordinate reset with the save queue, confirm that deletion succeeded, and reinitialize the account's revision before persisting the reset snapshot. Extend the browser test to reset, answer a question, confirm the new row was saved, and reload to verify that answer survives.
