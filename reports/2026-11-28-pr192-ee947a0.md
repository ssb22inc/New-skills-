## Assessment

I found several release defects after reviewing the changed code, generated public pages, and new tests. None of these are security holes or catastrophic medical mistakes, but three of them are public user-facing or evidence anomalies that should be fixed before release.

## Findings

### 1. [major] Legal page still claims it was updated on October 16

- **Where:** `pulsern/public/legal/index.html:2` · confidence high
- **Problem:** The PR changes the legal page content itself—the confidentiality copy, the payments heading, and the readiness-grading wording are all altered—but the visible 'Last updated: October 16, 2026' line remains unchanged. This means a user reading the page is told it has not been updated since October 16, 2026, even though terms text changed after that date.
- **How it fails:** User opens the legal page and sees a stale last-updated date, which is a false user-facing claim for a legal notice.
- **Fix:** Update the 'Last updated' date to the date this PR ships or to a date after all visible legal changes.

### 2. [major] Product screenshot manifest has stale source hash and commit

- **Where:** `pulsern/public/product/product-screenshots.json:24` · confidence high
- **Problem:** The manifest's sourceFiles entry for src/landing.jsx is still a7c69cc..., and its sourceCommitSha remains 44a566b..., even though this PR changes src/landing.jsx (FAQ copy, captions, and landing content). The recorded sourceSetSha256 therefore does not match the changed file.
- **How it fails:** Any product-image or release audit that verifies the manifest against the actual source tree will fail, or the manifest will falsely certify a page that no longer matches the recorded source set.
- **Fix:** Re-run the product-screenshot capture/generation step after the src/landing.jsx changes so the hashes and sourceCommitSha reflect the head commit.

### 3. [major] Learn index unconditionally claims every guide is RN-reviewed

- **Where:** `ops/build-learn.mjs:1` · confidence medium
- **Problem:** In renderIndex, the generated index always contains 'Sheldon Bennett, RN, writes and reviews every guide' and 'Every guide lists its sources and the RN who reviewed it.' But renderArticle has a pending branch that displays 'review evidence pending' when provenance.review.decision !== 'approved'. If any article is pending, the index public page misrepresents it as reviewed by an RN.
- **How it fails:** A pending guide exists (e.g., because a content hash or source-set hash changed and re-review is not yet complete). The /learn/ index tells users the guide was reviewed by an RN, while the guide page itself says review evidence is pending.
- **Fix:** Condition the index copy on whether all articles are approved, or phrase it as 'Each approved guide is RN-reviewed' and match the per-guide review line.

### 4. [minor] displayDate silently produces invalid dates for malformed input

- **Where:** `ops/author.mjs:51` · confidence medium
- **Problem:** displayDate accepts any pattern that matches YYYY-MM-DD and does not validate the month or day. Input like '2026-02-31' would render 'Feb 31, 2026' instead of failing.
- **How it fails:** A future malformed review or source date makes its way into the ledger and is published as a visibly impossible date on the public guide/about pages.
- **Fix:** Validate the date with Date.parse or a stricter calendar check before formatting.

### 5. [minor] No-op replace in homepage FAQ test

- **Where:** `tests/homepage-faq.test.js:13` · confidence high
- **Problem:** The test calls answer.replace("A 7-day free pass", "A 7-day free pass"), which is identical and does nothing. If it was meant to normalize or adjust the free-pass wording, it currently provides a false sense of safety about FAQ parity.
- **How it fails:** The test passes without fixing any real wording drift and the no-op obscures the intended check for future maintainers.
- **Fix:** Remove the no-op replace or replace it with a real normalization helper.
