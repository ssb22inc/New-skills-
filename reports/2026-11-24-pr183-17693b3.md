## Assessment

Needs revision for two keyboard-accessibility regressions. I did not establish a clinical-content or scoring defect from the supplied diff and images. Tests and build were not executed.

## Findings

### 1. [major] Arrow keys skip questions while an answer radio has focus

- **Where:** `pulsern/src/study-keys.js:21` · confidence high
- **Problem:** The new answer controls expose role="radio", but studyKeyAction treats ArrowLeft/ArrowRight on those controls as question navigation. There is no radio-group keyboard handler to consume the event. This gives the controls radio semantics without their expected keyboard behavior.
- **How it fails:** In Practice or a case step, a keyboard or screen-reader user focuses an answer radio and presses ArrowRight to select the next choice. The global handler instead calls onMove/onCaseMove, leaving the current question or step unscored and opening another one. Matrix answer radios have the same conflict.
- **Fix:** Implement arrow-key selection within each radio group and exclude radio targets from global back/next shortcuts. Add a browser regression that focuses an answer, presses ArrowRight, and verifies that the stem and recorded-answer count stay unchanged while the selected choice changes.

### 2. [major] The replacement lab search removes its visible focus indicator

- **Where:** `pulsern/src/App.jsx` · confidence high
- **Problem:** The new .lp-input rule sets outline:none, but neither the input nor .lp-search has a focus-visible/focus-within replacement. The permanently teal search border looks identical before and after focus. The previous search used .select, which has an explicit focus-visible outline.
- **How it fails:** A keyboard user tabs through the Study toolkit into the lab search field. There is no visible indication that typing will now enter a query, contrary to the project's focus-ring accessibility requirement.
- **Fix:** Restore a visible focus indicator in both themes, using an input :focus-visible outline or a distinct .lp-search:focus-within ring. Add a browser assertion for the focused search appearance rather than only testing that focus remains somewhere inside the dialog.
