## Assessment

Not ready to merge. The guest handoff still has cross-account privacy and data-loss paths, and legacy repeat detection and trial review scheduling are incomplete. These findings are based on the supplied changes; I did not execute the tests or build.

## Findings

### 1. [blocker] Sign-out leaves the held trial in sessionStorage

- **Where:** `pulsern/src/sign-out.js:8` · confidence high
- **Problem:** GuestTrial writes GUEST_HOLD_KEY to window.sessionStorage, but App passes window.localStorage to this helper. releaseHeldGuest(storage) therefore clears memory and the wrong storage area, leaving the sessionStorage copy readable after sign-out. The regression test masks this by using the same store for both holding and clearing the trial. The forced re-login path also does not clear the held copy.
- **How it fails:** Student A completes a trial, enters authentication, signs into an existing account, and signs out without adding the trial. Student B subsequently signs in on the same tab. readGuestForHandoff recovers A's retained trial from sessionStorage and offers it to B—or automatically merges it if B's account is new—exposing another student's study history and contaminating B's progress and ability estimate.
- **Fix:** Pass the local and session storage areas separately and clear the trial, held-trial key, and held memory on every sign-out path, including forced re-login. Test with two distinct storage objects and verify that a subsequent handoff finds nothing.

### 2. [blocker] Preserve the trial before every authentication transition

- **Where:** `pulsern/src/guest.jsx:92` · confidence high
- **Problem:** Only the SaveProgress card's two callbacks call holdGuestTrial. The header Sign in button, the question's Create a free account invitation, and the toolkit's sign-up invitations call the parent callbacks directly. Those callbacks unmount GuestTrial without preserving its in-memory answers.
- **How it fails:** localStorage.setItem fails because storage is full or restricted. After answering questions, the visitor taps Create a free account to ask beneath a rationale, or uses the header Sign in button. The trial component unmounts, no held copy exists, and the subsequent account load permanently loses those answers, XP, and review state.
- **Fix:** Create shared authentication-exit handlers inside GuestTrial that hold the current guest state before invoking onSignUp or onSignIn, and use them for every authentication CTA. Add a browser test where device writes fail and authentication actually replaces the trial component rather than merely incrementing a counter.

### 3. [major] Legacy case repeats require a field older saves never recorded

- **Where:** `pulsern/src/rewards.js:156` · confidence high
- **Problem:** The legacyAliases match requires row.source === "case", but the pre-change record function never persisted source, including for case-study steps. migrateBlob leaves those rows unchanged. Consequently, the legacy alias support does not recognize actual pre-change case answers. The N7 regression test passes only because its supposedly old rows are fabricated with the newly introduced source field.
- **How it fails:** A save contains the previously correct sepsis step { id: 101, cat: "Physiological Adaptation", diff: 3, correct: true }. After upgrading, answering case-sepsis-1 correctly is treated as a first answer and awards another 30 XP rather than returning the documented repeat result.
- **Fix:** Handle real legacy rows without source using an explicit migration/disambiguation policy for numeric bank-ID collisions. Replace the regression fixture with a serialized pre-change case answer and verify repeat behavior without adding new metadata to the fixture.

### 4. [major] Keep the scheduled review after a trial miss is corrected

- **Where:** `pulsern/src/guest.js:290` · confidence high
- **Problem:** The merge deletes a question's schedule whenever its latest trial answer is correct. Correcting a previously missed question is precisely when updateMissSchedule advances its next review date; a correct latest result does not mean the schedule should disappear. The existing tests incorrectly assert that deletion.
- **How it fails:** A visitor misses a question, resumes the trial the next local day, and answers its due review correctly. GuestTrial creates a future three-day review in guest.missSchedule. On account handoff, this branch deletes the prefixed schedule. Because the latest answer is now correct, neither reviewPools nor migration brings that scheduled retrieval back.
- **Fix:** Carry valid guest review schedules into the account under their prefixed IDs, including schedules for corrected misses. Test a wrong-answer → next-day correct-review → account-handoff sequence and assert that the future review date survives.
