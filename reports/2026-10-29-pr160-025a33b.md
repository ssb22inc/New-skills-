## Assessment

Changes requested. Operational failures can produce successful workflow runs, and the actual browser playback hook has no tests covering its safety-critical lifecycle behavior. This was a static review of the supplied files; tests and builds were not executed.

## Findings

### 1. [major] Fail the workflow when queued work encounters an operational error

- **Where:** `pulsern/ops/read-aloud-worker.mjs:271` · confidence high
- **Problem:** The final failure predicate ignores queued provider and save errors unless three occur consecutively. drainQueue records these errors in q.errors, but runJob only recognizes entries containing "could not read". A run can therefore report provider or storage errors in its summary while exiting successfully, contradicting the documented operational-failure behavior.
- **How it fails:** Queue one passage and run with max=1 while the speech endpoint returns 503. drainQueue returns retried=1 and an error, but providerDown remains false. There is no remaining prewarm allowance, and runJob returns failed=false. The same failure occurs with the default limit when the bank's weekly scan is already complete.
- **Fix:** Track operational failure explicitly in drainQueue and include it in runJob's failure result, independently of the consecutive-error threshold used to stop processing. Add a runJob test for a single queued provider failure with prewarming skipped or already complete.

### 2. [major] Test the actual playback hook's checked-audio and cancellation boundaries

- **Where:** `pulsern/tests/read-aloud.test.jsx:14` · confidence high
- **Problem:** The tests never mount useReadAloud. Controls are rendered with fabricated reader objects, while planReading and shouldAutoRead are tested separately. Consequently, none of the tests exercise the code that decides when Audio.play is called, cancels pending requests on item changes, or stops clinical audio when leaving an item. This is new critical playback logic without a test that would catch its failure.
- **How it fails:** Removing the hook's aborted-signal check after Promise.all, or bypassing its plan.kind guard, leaves this suite green. Those regressions could respectively start an old item's audio after navigation or attempt playback despite an incomplete/refused reading plan.
- **Fix:** Mount the real hook with controlled fetch responses and an Audio mock. Assert that unresolved/refused plans never start audio, a delayed response cannot start playback after the item changes or unmounts, and transitions between question and feedback stop the previous audio.
