## Findings

### 1. [blocker] Production aliases can bypass the diagram's visual attestation

- **Where:** `pulsern/ops/render-diagrams.mjs:50` · confidence medium
- **Problem:** The renderer disables the project's Vite configuration with configFile:false, while diagram-attest.mjs resolves imports by filesystem paths and omits Vite configuration from sourceKey. Consequently, an alias can change the drawing or clinical module used by production without changing the reviewed source graph or invalidating its signed approval.
- **How it fails:** After a diagram and map have valid signatures, a branch adds a Vite alias redirecting an existing drawing-helper import to src/clinical/alternate-kit.jsx. Keep the original files, facts and captions unchanged. The trusted renderer still draws the original helper, diagramSources still sends that original helper to the reviewer, and sourceKey remains unchanged. A normal Vite production build instead uses the alternate helper, including any incorrect drawing branches it contains. I could not inspect the repository's current build configuration, but this path is supported by normal Vite alias resolution.
- **Fix:** Preserve the prohibition on executing branch configuration, but reject unsupported or divergent build-resolution settings before approving diagrams. Ensure the renderer and attestation use the same validated module resolution as production, including relevant configuration and dependency inputs. Add an alias-redirection fixture proving that alternate clinical code is either rendered, reviewed and hashed, or refused.

### 2. [blocker] The dry-run safety test passes before the write path is reached

- **Where:** `pulsern/tests/diagram-gate.test.js:259` · confidence high
- **Problem:** Both dry-run invocations point Supabase at http://127.0.0.1:9. The database read fails before map-diagrams.mjs calls save(), and the test does not require a successful exit. Comparing files afterward therefore does not test the new DRY persistence guard.
- **How it fails:** Remove the if (!DRY) guard around the cache/map writes in save(). This test still passes because neither invocation reaches save(). Against a working bank, however, a keyless dry run treats approvals and decisions as unverifiable and overwrites a populated published map with an empty one—the exact destructive regression the test claims to prevent.
- **Fix:** Run against an isolated populated checkout and a successful fake bank response. Require exit status 0 and completion of the dry-run save/report path, then compare the populated map and decision cache byte-for-byte. Cover both public-key-only and keyless runs, and verify that removing the DRY guard makes the test fail.
