## Findings

### 1. [blocker] Unscoped legacy answers can disappear from both practice pools

- **Where:** `pulsern/src/state.js:16` · confidence high
- **Problem:** The comment says classifyLog runs after the catalogs return, but App never imports or invokes it. migrateBlob leaves legacy rows unscoped. For a stamped catalog question, settledResult then returns "pending", which excludes it from new questions, while scheduleEntry rejects its numeric schedule. unresolvedCards does not expose it either because the row lacks unclassified=true.
- **How it fails:** A cached pre-change app saves { id: 42, cat: "Pharmacology", correct: false } after migration 020 has already run. On the next load, bank:42 is neither new nor available in Review Misses or Today, even when its numeric review date is due. The one-time SQL update cannot protect subsequent legacy writes.
- **Fix:** Resolve unscoped rows on every load using an authoritative full-catalog resolver, or explicitly route unresolved rows into the unresolved-review flow. Do not leave them indefinitely pending. Add a full-App regression starting with an unscoped legacy miss after the one-time migration.

### 2. [blocker] Numeric review dates are lost when historical answers have different owners

- **Where:** `pulsern/supabase/migrations/020_relabel_legacy_progress.sql:173` · confidence high
- **Problem:** The migration collects every historical canonical owner of a numeric ID and transfers its schedule only when that entire set has one member. The old numeric schedule followed the most recent QBank answer, not every historical answer. Leaving it numeric makes it unusable when both corresponding catalog questions are present: scheduleEntry rejects numeric fallback when peerCounts is greater than one.
- **How it fails:** A student answered built-in question 7, then a different bank question 7 whose category lets the migration distinguish the sources. The bank question was missed and subsequently corrected, with a future review date under "7". Both log identities migrate successfully, but owners has two members, so the date stays under "7". Because the latest bank answer is correct, deriveMissSchedule adds no canonical replacement, and that scheduled bank review never returns.
- **Fix:** Determine schedule ownership from the latest applicable answer using log ordinality rather than all distinct historical owners. Preserve ambiguity when that latest owner genuinely cannot be established. Test the SQL migration itself with a built-in/bank collision and a corrected question carrying a future review date.

### 3. [blocker] Resolving one legacy miss rewrites every ambiguous answer with that number

- **Where:** `pulsern/src/App.jsx` · confidence high
- **Problem:** resolveLegacy maps claimLegacyRow over the entire log using only legacyId. Every unclassified historical row with that number receives the selected question's source and key, even though the unresolved card asks the student to identify a single recorded miss. Shared numeric IDs are precisely why those historical rows cannot safely be treated as one question.
- **How it fails:** An older log contains a correct answer to bank question 7 followed by a miss on built-in question 7, with both questions in the same category. Migration correctly leaves both ambiguous. Selecting the built-in question for the displayed miss also relabels the earlier bank success as builtin:7. The bank history is misattributed, and correcting the built-in miss earns zero XP as an alleged repeat instead of the correction bonus.
- **Fix:** Carry a stable log-entry identifier or index through the unresolved-review card and resolve only the answer the student identified. Leave other ambiguous entries untouched unless the student explicitly identifies them too. Add a regression with two historical sources sharing an ID and category.

### 4. [blocker] The rollback deletes exam attempts unrelated to this migration

- **Where:** `pulsern/supabase/rollback/rollback_relabel_legacy_progress_20261124.sql:10` · confidence high
- **Problem:** Migration 020 modifies progress blobs only, but its rollback deletes the entire live exam_attempts table and replaces it with a pre-change snapshot. Any readiness exam taken since that snapshot is erased even though the migration never changed it.
- **How it fails:** A student completes a readiness exam after deployment. Running this rollback to undo answer-ID relabeling deletes that attempt and restores the older attempt history. The student loses the recorded exam and can potentially retake a form that must never repeat.
- **Fix:** Remove the exam_attempts replacement from this progress-only rollback. Restore only the progress fields affected by the relabel, with safeguards against overwriting subsequent student activity, and test that post-migration exam attempts survive rollback.
