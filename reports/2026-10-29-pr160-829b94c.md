## Findings

### 1. [blocker] The mounted auto-read safety test never enables auto-read

- **Where:** `pulsern/tests/read-aloud-hook.test.jsx:159` · confidence high
- **Problem:** Earlier tests initialize the module-level prefsNow cache with auto=false. Clearing or writing localStorage does not invalidate that cache, so this test mounts with reader.prefs.auto still false. It therefore passes for the wrong reason and does not establish that switching a reader off prevents automatic playback.
- **How it fails:** Remove the key/off check from the hook's auto-start path: this mounted test still passes because auto-read is disabled throughout. The pure shouldAutoRead test does not cover whether the hook actually uses that guard.
- **Fix:** Reset or isolate the preferences module before loading auto=true, or enable auto-read through reader.setPrefs and then exercise a transition to an off reader with nonempty segments. Assert reader.prefs.auto is true before checking that no request or audio starts, and verify that bypassing the hook's off guard makes the test fail.

### 2. [major] Each passage creates a new audio element outside the Listen gesture

- **Where:** `pulsern/src/read-aloud.jsx:179` · confidence medium
- **Problem:** The first Audio element is created after session/network awaits, and subsequent elements are created after playback and a timer. On browsers requiring a user gesture for each new audible media element, notably restrictive Safari configurations, these play calls can reject with NotAllowedError. Returning to idle does not solve this: the next Listen action starts from segment zero again.
- **How it fails:** A student on a strict-autoplay browser presses Listen. Playback either never begins after the network response, or the stem plays after a cached retry but the next newly created element is blocked. Repeated Listen taps replay the stem rather than completing the question. FakeAudio.play always resolves, so the supplied tests cannot detect this. Real Safari behavior could not be verified from the supplied material.
- **Fix:** Use a persistent audio element and establish its playback permission within the user's Listen gesture, then reuse it for successive passages. Add browser coverage for an uncached first Listen and transition to the second passage under restrictive autoplay settings.

### 3. [major] Storage counter failures are indistinguishable from an exhausted budget

- **Where:** `pulsern/api/_speak.js:187` · confidence high
- **Problem:** Counter read/write failures return false from claimSlot, just like a genuinely full quota. The worker consequently classifies storage trouble as result="budget". Both queue draining and prewarming stop normally, and runJob can return failed=false, contradicting the documented promise that storage trouble fails the workflow.
- **How it fails:** Storage downloads still work, but listing or uploading usage/<day>/spend fails with a 500. No quota has been exhausted, yet every scheduled run stops without voicing anything, reports that today's budget is used up, and can remain green. The current counter-failure test only checks that spending stops; it does not check the workflow outcome.
- **Fix:** Distinguish quota exhaustion from counter/storage errors and propagate operational errors to runJob.failed while continuing to fail closed on spending. Add a runJob test with failing spend-counter reads or writes that asserts a failed workflow and a storage-error diagnostic.
