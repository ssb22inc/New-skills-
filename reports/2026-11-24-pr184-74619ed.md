## Assessment

Not ready to ship. The new guest flow exposes an incorrect anticoagulation item, and the save/reward integration has concrete data-loss and state-handling defects. Review was based on the supplied diff and images; tests and build were not executed.

## Findings

### 1. [blocker] Correct the warfarin item before serving it in the guest trial

- **Where:** `pulsern/src/guest.jsx:32` · confidence high
- **Problem:** The new guest pool includes built-in question id 3 (App.jsx lines 34–38), which keys vitamin K plus holding warfarin for an INR of 4.8 without bleeding. For INR 4.5–10 without bleeding, routine vitamin K is not recommended; holding warfarin with INR follow-up is usual unless additional bleeding-risk factors justify reversal. The stem supplies no such factors, and no option offers standard management.
- **How it fails:** An anonymous student receives question 3 and is taught that an INR of 4.8 without bleeding routinely warrants vitamin K.
- **Fix:** Revise the keyed option and rationale to reflect holding warfarin and monitoring/follow-up in the stated scenario, then pass the corrected item through the clinical accuracy gate.

### 2. [blocker] A skipped save is reported as success and deletes trial answers

- **Where:** `pulsern/src/App.jsx:350` · confidence high
- **Problem:** store.set returns normally when getSession yields no session. createSaveQueue interprets that return as a successful write, so the autosave completion handler clears the guest copy and can announce that the answers are in the account even though no upsert occurred. Queue invalidation only covers this component's explicit sign-out handler, not session expiration or an auth-driven unmount.
- **How it fails:** An existing user accepts the trial handoff as their session expires. The autosave's getSession returns null after a failed refresh; the task resolves successfully, and the only persisted copy of the trial answers is removed.
- **Fix:** Distinguish a persisted write from a signed-out/skipped operation. Clear the guest copy and show confirmation only after a successful upsert for the expected account. Invalidate pending save callbacks on unmount/auth changes, and test session loss between handoff and save.

### 3. [major] Malformed reward markers escape migration and crash the app

- **Where:** `pulsern/src/rewards.js:108` · confidence high
- **Problem:** migrateRewards accepts any integer rankHigh and copies badgesSeen without validating tier bounds. badgeBoard subsequently dereferences TIERS[earned].name, and CareerCard dereferences career.rank.name. Values such as badgesSeen.Pharmacology = 5 or rankHigh = 99 therefore pass parseProgress as readable progress but crash during rendering, bypassing the new unreadable-progress recovery screen.
- **How it fails:** A saved blob contains an out-of-range reward marker. Signing in repeatedly reaches the error boundary instead of loading with safe defaults or offering the protected recovery flow.
- **Fix:** Validate rank indices and badge tiers against their actual ranges during migration, defaulting invalid optional markers safely. Add both malformed-marker migration tests and a mounted-App recovery test.

### 4. [major] Rapid repeats still build correct runs and personal bests

- **Where:** `pulsern/src/App.jsx:931` · confidence high
- **Problem:** Run eligibility only excludes results whose reason is "too-fast". answerXp returns "repeat" before checking elapsed time, so a previously correct question answered in milliseconds is counted toward the run. guestAnswer uses the same eligibility check. This contradicts the adjacent guarantee that a too-fast tap never builds a run.
- **How it fails:** A student repeatedly reopens a completed case and rapidly taps its known answers. XP remains zero, but combos and longest-correct-run records continue increasing without meeting the reading-time floor.
- **Fix:** Compute time eligibility independently of the XP rejection reason and use it consistently for account and guest runs. Add a test with an earlier correct answer and an elapsed time below minThinkMs, asserting that the run does not advance.

### 5. [major] Undoing a card after midnight reverses the wrong day's ledger

- **Where:** `pulsern/src/App.jsx:948` · confidence high
- **Problem:** unnoteCard always adjusts today's reward entry, while the undo record stores only the prior schedule and XP—not the day originally credited. An undo after local midnight therefore leaves the original day's card count and XP intact. If no cards were graded on the new day, the early return skips the ledger reversal entirely even though lifetime XP is subtracted.
- **How it fails:** Grade Good for 5 XP before midnight, leave the tab open, then undo and regrade after midnight. The header ends with 5 XP, but the two daily entries total 10 XP and two reviewed cards for the single retained grade.
- **Fix:** Store the credited local day with each undo record and pass it to the reward-ledger reversal. Only decrement daily.answered when it belongs to that credited day. Test grade → midnight → undo → regrade through the actual handlers.
