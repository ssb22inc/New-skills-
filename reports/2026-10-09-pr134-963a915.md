## Assessment

Do not merge yet. The review collector can omit executable changes, narration QA can approve a clinically altered transcript, and the workflow save retry can lose paid results while reporting success. ## Findings

### 1. [blocker] Binary-classified source can bypass the review payload

- **Where:** `pulsern/ops/astra-review.mjs:228` · confidence high
- **Problem:** Ordinary source files use git's default binary detection. If git classifies a file as binary, its diff contains only a 'Binary files differ' marker. When the post-change file exceeds MAX_FULL_FILE_CHARS, planContext also excludes its full contents. Nothing rejects this unreviewed payload before a successful model response becomes a passing status.
- **How it fails:** A PR inserts a NUL inside a JavaScript block comment near the beginning of an executable source file and pads it beyond 60,000 characters. JavaScript comments can contain that character, but git treats the file as binary. Functional changes elsewhere in the file are absent from the model's prompt; the trusted workflow can certify the commit without showing those changes.
- **Fix:** Force textual diffs for supported source formats, safely represent control characters, and fail closed whenever changed content cannot be represented in the review payload. Binary assets need an appropriate review representation or an explicit failure, not just a git marker. Add a real-git regression using an executable source file above the full-file limit with a NUL in a comment.

### 2. [blocker] Narration QA discards clinically meaningful percent symbols

- **Where:** `pulsern/ops/narrate-lib.mjs:167` · confidence high
- **Problem:** Both speechTokens and normaliseSpeech discard '%' as punctuation. Consequently, the new exact-word check still treats a number and a percentage as equivalent, despite their different clinical meanings.
- **How it fails:** Take the passing hand-written abg/lungs transcript in tests/narrate.test.js and replace 'above 45' with 'above 45%'. audioCheck still passes: both normalized token streams are identical. A recording that incorrectly says 'forty-five percent', transcribed as '45%', can therefore be published as the PaCO2 teaching threshold.
- **Fix:** Normalize clinically meaningful symbols into explicit tokens, such as '%' to 'percent', instead of deleting them. Preserve or reject other unit-bearing symbols deliberately. Add positive-baseline and corrupted-percentage tests against the actual scripts, bump QA_VERSION, and recheck recordings approved by the weaker rule.

### 3. [blocker] A rebase conflict can be reported as a successful save

- **Where:** `.github/workflows/pulsern-diagram-map.yml:113` · confidence high
- **Problem:** The save loop ignores a failed rebase with '|| true' and then retries pushing HEAD. During a conflicting rebase, HEAD can already be the remote branch tip, without the results commit. Pushing that HEAD succeeds as an up-to-date no-op, so the job reports 'Saved' and sets pushed=true even though its paid results were never pushed. The diagram-review and narrate workflows contain the same pattern.
- **How it fails:** While the mapper runs, another commit updates the same map or decision-cache file. The initial push is rejected, and rebasing the mapper's results commit conflicts. The next push publishes nothing but succeeds because HEAD equals the remote tip. The runner then exits successfully and is discarded, taking the unpushed decision cache with it.
- **Fix:** Do not continue the push loop after an unresolved rebase. Preserve results as an unconditional artifact before attempting synchronization, fail explicitly on conflicts, and only report a successful save after verifying that the results commit or its successfully rebased equivalent reached the branch. Apply the fix to all three workflows and test a conflicting concurrent update with real git repositories.

### 4. [major] Reused decisions retain the obsolete question fingerprint

- **Where:** `pulsern/ops/map-diagrams-lib.mjs:129` · confidence high
- **Problem:** The browser fingerprint now includes options and answer, but buildItemMap still copies the cached d.fp unchanged. Cache freshness checks itemHash, diagramHash and extracted values, none of which invalidates a decision solely because the fingerprint algorithm changed.
- **How it fails:** A decisions.json cache produced by the previous mapper contains a confirmed potassium or pressure-injury pairing whose question, diagram content and extraction remain unchanged. After obtaining current visual approvals, the mapper skips the paid pairing review and emits the old stem/rationale-only fingerprint into a version-2 map. pairsFor computes the new fingerprint and silently suppresses the pairing. The shipped-map tests accept the old value because it is still eight hexadecimal characters.
- **Fix:** Recompute the browser fingerprint from the current question whenever publishing a fresh cached decision; this does not require another paid review because itemHash already binds the reviewed question fields. Alternatively, version and migrate the cached fingerprint. Add a producer-to-consumer regression starting with an actual old-format cached fingerprint.
