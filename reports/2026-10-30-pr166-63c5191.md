## Assessment

The new time limit can prevent the bank scan from ever advancing while still requesting successive workflow runs. The added cached-scan test does not detect this resumability defect.

## Findings

### 1. [major] Deadline exits do not save progress within a passage group

- **Where:** `pulsern/ops/read-aloud-worker.mjs:250` · confidence high
- **Problem:** Returning "max" here saves only the current kind and previous completed item ID, not the position within `texts`. The next run rereads the same cached passages from the beginning. If the remaining run time is consistently shorter than that rescan, the cursor never advances. `runJob` nevertheless returns `more: true`, and cached reads consume no spending slots to stop the chain.
- **How it fails:** Start with all 47 verdict passages cached and allow enough time for only three record reads per run—the state already constructed by the new cached-scan test. Every run reads those same three records, saves a cursor still pointing at `verdicts`, and dispatches another run without reaching the questions. This can also occur within a bank item when storage is slow or queue processing leaves little time. The test checks only that `done` is falsy, so it passes without proving that any resumable position was kept.
- **Fix:** Persist a resumable position within the current passage group, including verdicts, and resume after the cached passages already visited. Add a regression that invokes multiple deadline-limited runs against the same storage and verifies that successive runs advance through distinct passages and eventually leave the group.
