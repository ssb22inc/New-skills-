## Findings

### 1. [blocker] Multiple record calls before a render overwrite earlier answers

- **Where:** `pulsern/src/App.jsx:965` · confidence medium
- **Problem:** record derives next.log, next.xp, next.ability and next.daily from render-captured state, then replaces those states directly. Only run and rewards have synchronously updated refs. Two calls before React commits therefore both start from the same log and XP, and the second replaces the first call's answer. The previous functional log and XP updates did not have this problem.
- **How it fails:** A readiness-exam submission delivers several scored items before React renders again. After record(q1) and record(q2), the saved log contains only q2's new row, XP reflects only its award, and ability reflects only its update. The supplied exam tests substitute their own record callback rather than exercising App's implementation. The unchanged ExamCenter implementation was not supplied, so I could not verify whether it forces a React commit between every result.
- **Fix:** Apply answers sequentially against one authoritative current progress state, using a reducer or synchronously maintained state ref, rather than independently captured state fields. Add an integration test that sends multiple exam results through the real App recorder without an intervening render and verifies every log row, XP award and ability update.

### 2. [blocker] Historical replay discards ability contributed by legacy answers

- **Where:** `pulsern/src/answer-apply.js:37` · confidence high
- **Problem:** replayAbility resets every category to emptyAbility and skips every row without a canonical identity or marked unclassified. Those rows can nevertheless have contributed to the account's persisted ability. Importing one earlier trial answer can consequently erase existing ability history, including categories unrelated to the imported answer.
- **How it fails:** An account has legacy Management of Care history contributing theta 1450 and n=100, plus a newer timestamped answer. An older trial answer is imported while catalog classification is unavailable, or while some legacy identities remain ambiguous. insertedBehind selects replayAbility, which skips the legacy rows and resets Management of Care to theta 1200 and n=0. The corrupted ability is then autosaved and used for readiness and adaptive selection.
- **Fix:** Preserve the aggregate ability baseline for history that cannot be faithfully replayed. Replay only a suffix with complete identity and rating information, or defer chronological insertion until a safe reconstruction is possible. Add a regression test with persisted legacy ability, unscoped historical rows and a timestamped newer answer.

### 3. [major] Legacy fallback assigns explicitly ambiguous history to the current question

- **Where:** `pulsern/src/question-review.js:60` · confidence high
- **Problem:** unscopedRows includes rows marked unclassified, and settledResult resolves them whenever the current question list contains one numeric peer. That list is not the complete identity catalog: it can contain only bank questions, omit bundled questions after bank loading, exclude cases, or already be filtered. scheduleEntry makes the same local-list assumption. This undoes classifyLog's explicit ambiguity decision.
- **How it fails:** Legacy id 101 matches both a bank question and the bundled sepsis case step, so classifyLog correctly marks it unclassified. QBank contains bank question 101 but no case steps. settledResult now treats the old case result as that bank question's result: a correct case answer hides an unseen bank question, while a wrong result or raw schedule incorrectly places it in Review Misses.
- **Fix:** Do not resolve explicitly unclassified rows through raw-id fallback. Resolve legacy identities against the complete source catalogs once, and preserve unresolved status when selecting, filtering or removing held questions. Test ambiguity between a bank question and a case step while only the bank question is present in QBank.

### 4. [major] Correct legacy reviews do not advance their raw-key schedule

- **Where:** `pulsern/src/answer-apply.js:137` · confidence high
- **Problem:** The review reader accepts a legacy schedule under the numeric id, but applyAnswer updates only q.key. When the canonical entry has not yet been migrated, updateMissSchedule sees a correct answer with no entry and returns the map unchanged. The raw due date remains active.
- **How it fails:** A saved miss has schedule[42] due today. The loaded bank question is stamped bank:42, but case-catalog loading is delayed or fails, so App's rekeying effect has not run. Review Misses serves question 42 through scheduleEntry's fallback. Answering correctly creates no bank:42 schedule and leaves schedule[42] due today, so subsequent sessions keep serving the supposedly completed review instead of moving it three days out.
- **Fix:** Normalize the resolved legacy schedule into the canonical key before grading, or pass the schedule entry actually used to serve the question into the update. Ensure the old entry cannot remain independently active. Test a correct review of a raw-key legacy schedule before catalog migration completes.

### 5. [major] An imported earlier study day never joins an existing streak

- **Where:** `pulsern/src/answer-apply.js:126` · confidence high
- **Problem:** Historical answers use the live advanceStreak function against the account's latest streak. For an earlier imported day, advanceStreak deliberately returns unchanged because the saved lastDay is in its future. Although the answer is inserted chronologically and credited to rewards.days, the streak is never reconciled.
- **How it fails:** The account first studied Tuesday and has count=1, lastDay=Tuesday. A Monday trial answer is then added with consent. The resulting log and day ledger contain study on Monday and Tuesday, but the streak remains one day instead of two. Previously spent shields or covers likewise are not reconciled when an imported answer fills a protected day.
- **Fix:** Handle historical streak reconciliation separately from the live clock-change safeguard. Recompute the affected dated segment while preserving the baseline before that segment, including shield and cover consumption. Add tests for an imported day immediately preceding the current streak and for an imported answer filling a covered day.
