## Findings

### 1. [major] maybeGrantCover marks a week as cover-granted even when the bank is full

- **Where:** `pulsern/src/rewards.js` · confidence medium
- **Problem:** In `maybeGrantCover`, when the student already has `covers === MAX_COVERS` and completes 5 shifts, the function still appends `wk.monday` to `coverWeeks` and returns `granted: false`. The cover count is not increased, so the earned cover is effectively discarded. Because `coverWeeks` now contains that week, a later call in the same week returns early and cannot grant the cover even after the student spends a cover and has room again.
- **How it fails:** A student has 2 banked covers, completes 5 shifts in a week, then uses one cover later that same week. At that point `covers` becomes 1, but `coverWeeks` still contains the week's Monday, so `maybeGrantCover` keeps returning early and never restores the cover they earned while at the cap.
- **Fix:** Do not append the week to `coverWeeks` unless the cover is actually banked (`rewards.covers < MAX_COVERS`), or otherwise make the same-week spent cover refundable from an earned-but-unrecorded cover.

### 2. [major] Cover cap regression test misses the lost-earned-cover path

- **Where:** `pulsern/tests/rewards.test.js` · confidence high
- **Problem:** The test for `mayGrantCover` at max covers only asserts `capped.rewards.covers === MAX_COVERS`. It does not assert that `coverWeeks` was left unchanged or that spending a cover later in the same week re-grants the cover. As written, the test passes even though the implementation can lose the earned cover.
- **How it fails:** The existing test suite is green, but the defect above is not caught because the test does not exercise the `coverWeeks.includes(monday)` early-return path after a cover is spent.
- **Fix:** Add a test that starts with `covers === MAX_COVERS`, completes 5 shifts, then simulates spending a cover and checks whether the cover earned during that week is banked.

### 3. [major] Garbled label in today dashboard

- **Where:** `pulsern/public/product/pulsern-today-dashboard.png` · confidence high
- **Problem:** The after version of the today dashboard displays the text 'Day 0-7 to 7' in the streak-shield row. This is a misleading, unreadable label; it appears to be a typo or rendering error (likely intended to be 'Day 0 of 7' or 'Day 0-7'). This is a real defect on a plausible user-facing path.
- **How it fails:** A student viewing the Today dashboard sees an incoherent streak-shield status ('Day 0-7 to 7') instead of a clear day indicator, reducing trust in the UI.
- **Fix:** Replace the 'Day 0-7 to 7' label with a clear, correct day indicator such as 'Day 0 of 7' or 'Day 0-7'.

### 4. [minor] Persisted `rewards` shape documented out of date: `cardOps` is omitted

- **Where:** `pulsern/PULSERN_BUILD.md` · confidence medium
- **Problem:** The BUILD.md reward bullet lists `prefs` but does not mention `cardOps`, which `src/rewards.js` persists and `migrateRewards`/`mergeRewards` handle. A future integration following the frozen-contract doc may treat `cardOps` as garbage or fail to preserve it.
- **How it fails:** A future maintainer writes a task to inspect or migrate the blob using BUILD.md §4 and loses card-operation history because the authoritative-looking shape omits that additive field.
- **Fix:** Add an explicit note in the BUILD.md rewards shape that `cardOps` is an optional additive array, or update the authoritative `src/state.js` comment to point to the new location of the authoritative shape.
