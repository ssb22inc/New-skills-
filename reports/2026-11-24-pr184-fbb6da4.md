## Findings

### 1. [blocker] Numeric aliases can identify an unrelated bank answer as the trial question

- **Where:** `pulsern/src/guest.js:230` · confidence high
- **Problem:** guestImportIdentity adds the bare numeric ID as an alias merely because that number appears in builtIns. The account log does not establish that a row with that ID came from the bundled question. App always supplies QUESTIONS, so an unrelated shared-bank answer with the same number is treated as prior exposure, suppressing XP, ability updates and day credit.
- **How it fails:** An account has answered shared-bank question 7, whose stem differs from bundled question 7. The student subsequently imports a trial answer to bundled question 7. sameAnswer matches the bank row through alias "7", and alreadyAnswered becomes true even though these are different questions. The genuinely new trial answer is then omitted from the ability update.
- **Fix:** Match imports using verified content identity or explicit bundled-item provenance, not a bare numeric alias. Preserve ambiguous legacy rows without assuming their source. Add an end-to-end mergeGuestIntoBlob regression with an unrelated bank item sharing a bundled ID; the existing linkBuiltInGuest helper test does not exercise this path.

### 2. [blocker] New trial attempts are logged but omitted from ability updates after prior exposure

- **Where:** `pulsern/src/guest.js:282` · confidence high
- **Problem:** The alreadyAnswered guard skips updateAbility for every question previously encountered by the account, including a newly imported correction of an earlier miss. These are distinct attempts, already deduplicated by attempt ID. Normal signed-in review answers update ability, but the same outcome imported from the trial does not.
- **How it fails:** The account previously imported guest-1 as incorrect. A later trial answers that question correctly and the student chooses Add. The successful attempt is appended to the log and contributes to answer counts and recent accuracy, but the category theta and n remain unchanged. Readiness therefore uses inconsistent evidence depending on which screen recorded the correction.
- **Fix:** Apply the normal ability update to each newly accepted attempt. Use attempt IDs to prevent duplicate incorporation and question history only for the XP policy. Test that a later imported correction produces the same ability state as recording that correction through signed-in practice, while retrying the same import changes nothing.

### 3. [major] Legacy database-case answers never satisfy the repeat guard

- **Where:** `pulsern/src/rewards.js:188` · confidence high
- **Problem:** Matching a legacy case ID requires row.source === "case", but the pre-change record function did not persist source. tagLegacyCaseRows only recognizes the bundled cases' 100–125 IDs, so old database-case rows such as 50072 remain untagged and cannot match case-db7-2. The database-case regression in tests/review3.test.js supplies source: "case" manually, testing a state the old app never produced.
- **How it fails:** A student previously answered database case 7, step 2 correctly, leaving an old log row with id 50072 and no source. After upgrading, answering that step again is classified as a first correct answer and pays another full 30 XP instead of the documented repeat payout of zero.
- **Fix:** Resolve legacy database-case identities using verified case and question metadata, with collision handling, rather than requiring an absent historical marker. Change the regression fixture to an actual pre-change blob without source and run it through the shipped migration and repeat-detection path.

### 4. [major] Imported correction XP disappears from the daily and weekly ledger

- **Where:** `pulsern/src/guest.js:302` · confidence high
- **Problem:** Day XP is recorded only when the group contains a question not previously answered by the account. A later trial correction can legitimately earn REVIEW_FIX_BONUS while every row has alreadyAnswered set, causing the account XP to increase without recording that XP in rewards.days.
- **How it fails:** An account previously missed guest-1 and imports a later considered correct attempt. The handoff summary and header gain 5 XP, but fresh.length is zero, so no bumpDay call occurs. This week's rounds continues to report zero XP for that work.
- **Fix:** Record earned XP for every newly imported attempt independently of whether it qualifies for fresh-question or streak credit. Add a regression asserting that an imported repeat correction adds the same bonus to total XP and the appropriate local day's XP ledger.
