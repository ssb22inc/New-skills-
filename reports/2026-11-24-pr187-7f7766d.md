## Findings

### 1. [blocker] Invalid final reviews are discarded instead of failing the gate

- **Where:** `pulsern/ops/astra-review.mjs:510` · confidence high
- **Problem:** parseReviewText silently ignores candidates that fail validateResult and accepts any remaining valid object. This makes an earlier example with empty findings sufficient for a PASS even when the actual final review is malformed. The two-verdict test covers only two schema-valid objects, not this fail-open case.
- **How it fails:** The response contains {"assessment":"Example","findings":[]} followed by a final review containing a major finding whose fix field is missing. The final review fails validation and is discarded; the example survives, so runReview returns code 0 and the workflow posts success. Previously, this multi-object response failed JSON.parse.
- **Fix:** Accept only a complete, unambiguous review after removing explicitly supported wrappers. A review-shaped object that fails validation, or an incomplete final object following an example, must invalidate the response rather than be treated as prose. Add an end-to-end regression test with a valid empty example followed by an invalid final review and assert a failure.

### 2. [major] Search review no longer runs on every change as required

- **Where:** `.github/workflows/pulsern-seo-guardian.yml:140` · confidence medium
- **Problem:** The new condition skips both the model call and report enforcement for non-marketing changes. The supplied project rules explicitly require this review to run on every change and leave a complete, valid report, even though its completed FAIL verdict is advisory. The later exception is asserted only inside this PR's CLAUDE.md edit; I could not verify authorization for that policy change.
- **How it fails:** An app-only or models.mjs-only PR produces changed=false. Assuming the deterministic checks pass, the search gate succeeds without invoking seo:adversary or requiring its report. Scheduled and manually dispatched runs also always take this skip path.
- **Fix:** Restore unconditional review execution and report enforcement under the supplied rules. If the owner intends to narrow that requirement, obtain authoritative confirmation of the amendment before weakening the workflow.

### 3. [major] Standard side-effect imports are missing from the marketing dependency graph

- **Where:** `pulsern/ops/seo-page-change.mjs:16` · confidence medium
- **Problem:** IMPORT_RE follows from-imports, dynamic imports, and new URL expressions, but not side-effect imports such as import "./landing.css". Consequently, the detector does not fulfill its documented promise to include every local file imported by the homepage and builders. The added tests check selected repository paths but do not exercise this dependency form.
- **How it fails:** With a standard Vite side-effect CSS import in landing.jsx, a subsequent CSS-only change can alter visible generated text or hide a disclaimer while marketingPagesChanged returns false and skips the scoped review. The supplied files do not establish whether the current landing page already uses this import form, but the detector's omission is reproducible.
- **Fix:** Include side-effect imports in dependency discovery, preferably using the build system's resolved dependency graph rather than a partial import regex. Add a fixture containing a side-effect import and verify that changing only the imported file requires review.
