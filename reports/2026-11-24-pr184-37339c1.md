## Assessment

Do not merge yet. Trial imports can discard answers while reporting success, sign-out recovery can lose unsaved progress, and legacy misses can disappear from review. The timeout backup also leaves full account history readable after sign-out. Tests were not executed; the existing-account browser test visibly contradicts the merge implementation.

## Findings

### 1. [blocker] Existing-account imports report saved answers without retaining them

- **Where:** `pulsern/src/guest.js:378` · confidence high
- **Problem:** importTrialOntoHistory adds XP and review dates but returns the original log, ability, and daily counters unchanged. App nevertheless confirms that the trial answers are in the account and count toward stats, badges, and readiness, then deletes the device copy. Built-in misses can also become unreachable after the shared bank loads because expandTrialQuestions restores built-ins from log rows, which this branch never adds.
- **How it fails:** An account with 30 previous answers accepts two trial answers using Add to my account. Its log still contains only 30 answers, but the confirmation reports two imported answers and the trial copy is cleared. The new progress-load-browser test expecting two builtin log rows would fail against this implementation.
- **Fix:** Retain accepted trial answers using a chronology-aware, idempotent merge that preserves existing account results and consistently updates the promised statistics. Ensure imported misses remain reviewable after the bank loads. Add end-to-end assertions covering the saved log, statistics, reload, and Review Misses before clearing the trial copy.

### 2. [blocker] Recovery compares against an obsolete server snapshot and drops newer answers

- **Where:** `pulsern/src/progress-load.js:81` · confidence high
- **Problem:** readPendingProgress requires baseRaw to equal the current server row, but App's serverRawRef is populated only during the initial read and is never advanced after successful autosaves. Consequently, a timeout recovery snapshot is normally rejected once any earlier save in that session has changed the cloud row. The subsequent successful autosave clears that rejected recovery copy.
- **How it fails:** The app reads row A, successfully saves answer one as row B, then the write containing answer two hangs. Sign-out stores the latest payload with baseRaw A. On the next sign-in the server returns B, so the recovery payload is ignored and later deleted; answer two is permanently lost.
- **Fix:** Track the last confirmed server revision throughout the save queue, using a server revision or normalized representation rather than an initial raw JSON string. Preserve conflicting recovery snapshots for explicit reconciliation instead of silently clearing them. Test read A, successful save B, hung save C, sign-out, and sign-in against B.

### 3. [blocker] Timeout sign-out leaves full account progress readable on the device

- **Where:** `pulsern/src/progress-load.js:71` · confidence high
- **Problem:** The timeout path stores the entire signed-in progress blob in plaintext localStorage under a user-ID-prefixed key. Sign-out clears the old backup and guest keys but deliberately leaves this replacement backup behind, without an expiry. The user-ID check in readPendingProgress does not protect direct access to the stored value.
- **How it fails:** A student signs out on a shared computer while a save hangs. The next person can inspect localStorage without signing into that account and read the former student's answer history, exam results, exam date, and account identifier. The copy can remain indefinitely if the original student does not return and save successfully.
- **Fix:** Do not retain plaintext account-history backups after sign-out. Use authenticated server-side recovery or encryption whose decryption key is unavailable after logout. If safe recovery storage is unavailable, explicitly offer a user-controlled download or warn before discarding unsaved work.

### 4. [blocker] Ambiguous legacy IDs silently remove existing misses from review

- **Where:** `pulsern/src/question-key.js:73` · confidence high
- **Problem:** A legacy numeric answer whose ID occurs in both the bundled and bank catalogs is marked unclassified. historyIndex then excludes its result, scheduleEntry refuses its old numeric schedule, and unseenQuestions treats the question as new. The log row survives, but the protected Review Misses behavior does not.
- **How it fails:** A legacy save contains a wrong answer for ID 7 and its review date. When the loaded bank also contains ID 7, classification marks the row unclassified. That miss disappears from Review Misses and Today, and the bank question becomes available as new—even if the miss was reviewable before the catalog queries completed.
- **Fix:** Keep ambiguous legacy misses recoverable rather than silently excluding them and presenting them as unseen. Resolve identities from trustworthy historical provenance where available; otherwise expose an unresolved-review state with an explicit resolution path. Add a migration test proving that catalog collisions do not make an existing miss inaccessible.
