### 2. [major] Index and about pages unconditionally claim every guide is reviewed by the RN

- **Where:** `ops/build-learn.mjs` · confidence high
- **Problem:** renderIndex prints 'Every guide is written and reviewed by ' + review author, and build-public-pages aboutPage prints 'Sheldon writes and reviews every public study guide on this site.' These are emitted unconditionally, before checking guide approval status. The same build pipeline explicitly renders an article with 'review evidence pending' when provenanceFor returns decision !== approved. So the visible library page (and about page) can make a statement that is false for any published pending guide.
- **How it fails:** An ARTICLES entry lacks a matching approved record in content-review-records.json (or hashes drift). build-learn still writes the guide page with a pending review line, but public/learn/index.html says every guide is reviewed by the RN.
- **Fix:** Make the index and about-page wording conditional on whether all guides are approved (or value precision over marketing: only write reviewed-guide claims for approved routes).

### 3. [major] About page asserts Florida RN license even when the page hides the verification link

- **Where:** `ops/build-public-pages.mjs` · confidence medium
- **Problem:** aboutPage hardcodes 'Sheldon Bennett, RN, a Florida-licensed nurse since 2020' in the meta description and inserts AUTHOR_SENTENCE in visible body, but uses REVIEWER_VERIFIED only to show/hide the license-lookup link. If reviewer.verificationStatus is not 'verified' (or the URL is not https) — a state the same code handles in methodology with 'credential verification pending' — the about page still makes the affirmative licensure claim.
- **How it fails:** Set reviewer.verificationStatus to 'pending' in content-review-records.json and rebuild. /about/ says he is a Florida-licensed nurse since 2020 but gives no verification link, while /methodology/ says verification is pending.
- **Fix:** Gate the licensure wording on REVIEWER_VERIFIED, or otherwise consistently show the evidence/pending state.

### 4. [minor] No-op replace in FAQ parity test

- **Where:** `tests/homepage-faq.test.js` · confidence high
- **Problem:** The expectation maps answers through `answer.replace("A 7-day free pass", "A 7-day free pass")`, which does nothing and only looks like normalization. It does not make the test pass falsely, but it is dead code that makes the test harder to read and invites future drift.
- **How it fails:** No direct runtime failure; maintainability concern.
- **Fix:** Remove the no-op replace and compare `answer` directly.

### 5. [minor] Legal page 'Last updated' date is not updated for this PR's content changes

- **Where:** `public/legal/index.html` · confidence medium
- **Problem:** The page still says 'Last updated: October 16, 2026' while this PR changes the visible text (privacy list wording, payments subheading, grading note, and the h1). The date is therefore stale and says the page was last reviewed earlier than its current content.
- **How it fails:** A reader sees the current page text with a last-updated date before these changes.
- **Fix:** Update the last-updated date to the date this legal page content was actually changed.

### 6. [minor] displayDate can emit 'undefined 40, 2026'

- **Where:** `ops/author.mjs` · confidence medium
- **Problem:** The function's regex accepts month `13` or day `40`, and `MONTHS[12]` is undefined, so it can render an invalid date as `undefined 40, 2026`. Most callers pass previously validated ISO dates, so this is unlikely on current data, but it is not a strong formatter.
- **How it fails:** Call `displayDate('2026-13-40')`; it returns 'undefined 40, 2026' instead of failing/returning the original string.
- **Fix:** Validate month/day ranges and fall back to the original value or throw for invalid dates.
