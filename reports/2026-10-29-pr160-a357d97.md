## Assessment

Not ready to merge. The speech normalizer can remove a clinical math operator, and the demand queue does not consistently deliver the documented whole-item preparation or fresh-request priority. I reviewed the supplied code and tests; I could not execute them or inspect the live bank.

## Findings

### 1. [blocker] The speech normalizer removes multiplication operators

- **Where:** `pulsern/src/read-aloud-script.js:48` · confidence medium
- **Problem:** Every space-delimited middle dot is converted to a comma, including a middle dot used for multiplication in a dosage-calculation explanation. The accuracy check compares audio against this already-altered script, so it cannot detect the lost operator.
- **How it fails:** An approved explanation containing "0.1 mg/kg · 70 kg = 7 mg" becomes "0.1 milligrams per kilogram, 70 kg = 7 mg". Audio omitting the multiplication operation can then pass the check and reach a student. I could not verify whether the live bank already contains this notation.
- **Fix:** Distinguish layout separators from mathematical operators. Translate multiplication dots to "times" in calculation expressions, and withhold ambiguous passages rather than silently deleting their operation. Add a regression test covering a clinical calculation, not just a title separated by a middle dot.

### 2. [major] Demand preparation queues only the requested side or phase

- **Where:** `pulsern/api/_speak.js:555` · confidence high
- **Problem:** The queue loop uses parts returned by scriptFor(ref, item), which contains only the requested ref.part and, for cases, the requested step. It does not queue the question's explanation, a card's opposite side, or the remaining case steps. This contradicts the worker and route documentation that a request prepares every part of the item together.
- **How it fails:** Before prewarming reaches a card, a student presses Listen on its front. Only the front is queued. After the worker voices it, flipping the card produces another preparation delay because the back was never queued. The same repeated delay occurs between a question and its explanation or between case steps, particularly when queued work consumes the run's capacity.
- **Fix:** Enumerate and queue all voiceable parts of the admitted bank item, using appropriate references for each side, step and feedback passage, while keeping playback restricted to the current screen phase. Add tests asserting that one front/question/intro request queues the other parts without separately requesting them.

### 3. [major] Deleting queue entries invalidates offset pagination

- **Where:** `pulsern/ops/read-aloud-worker.mjs:83` · confidence high
- **Problem:** laneEntries advances its offset by 1,000 while drainQueue removes entries from that same listing. After the first page is deleted, the remaining entries shift toward offset zero, so the next listing skips them. This can let retries run before pending fresh requests.
- **How it fails:** Suppose queue/ contains 1,000 already-decided entries left after a removal outage, followed by a pending fresh request. Once removal recovers, the worker deletes the first 1,000 entries, then lists at offset 1,000 and misses the fresh request now at offset zero. It proceeds to queue-retry/ and spends capacity there instead. The existing 450-entry recovery test never crosses this pagination boundary.
- **Fix:** Use pagination that remains valid while deleting, such as a stable keyset cursor with deterministic ordering, or explicitly account for removed entries when advancing the offset. Add a regression test with more than 1,000 removable entries followed by fresh work and a retry, asserting that fresh work is reached first.
