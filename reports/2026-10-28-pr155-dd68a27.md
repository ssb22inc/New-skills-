## Assessment

The bank-reader credentials are isolated from the branch code, but the practice-bank data is not: untrusted branch code can return it through the prepared artifact. The new network-blocking test does not cover this return channel.

## Findings

### 1. [blocker] Untrusted matcher can exfiltrate practice-bank content via the prepared artifact

- **Where:** `pulsern/ops/map-diagrams.mjs:185` · confidence high
- **Problem:** The prepare path passes question stems, options, and rationales to the branch's matcher in the browser, then accepts its returned `proposed` value and serializes it into the prepared map without validating or reconstructing the output. The browser's network isolation does not prevent code from returning data to the trusted Node process through `call("propose", ...)`.
- **How it fails:** A malicious branch changes `proposePairs` to return question text or rationales inside proposal fields. The trusted script writes those values into `map.json`, and the workflow uploads that file as an artifact. A branch author or other repository reader can download the artifact and recover protected bank content; rationales may also disclose answers.
- **Fix:** Do not pass protected bank rows to untrusted branch code. Run the matcher from trusted code, or otherwise redesign the prepare flow so untrusted code never receives the bank data. Treating the browser as offline is insufficient: validate and reconstruct all returned data using a strict allowlist, and do not publish attacker-controlled proposal output in an artifact. Add a test that makes the matcher encode supplied question content into its return value and verifies the artifact cannot contain it.
