## Assessment

Not ready to merge. The persistence changes can discard post-reset answers, roll back newer flashcard schedules, and restore XP that the student explicitly erased.

## Findings

### 1. [blocker] Preserve resetGeneration when loading saved progress

- **Where:** `pulsern/src/state.js:20` · confidence high
- **Problem:** migrateBlob drops resetGeneration. App.applyBlob consequently resets resetGeneration.current to 0 when loading a saved generation-1 account. Subsequent saves are treated by reconcileProgress as pre-reset snapshots and replaced wholesale by the server blob.
- **How it fails:** Reset progress, let it save, then reload with a slow connection. Answer a question before the initial autosave response arrives. That answer's payload omits resetGeneration, so the generation comparison returns the saved reset blob instead. The reconciled response is applied to the screen, removing the new answer and its ability, XP, and review updates.
- **Fix:** Round-trip resetGeneration through migrateBlob using the same validation as reconcileProgress. Add a migration round-trip test and a browser regression that delays the first post-reload save while a new answer is recorded.

### 2. [blocker] Do not treat every field in an old snapshot as a new edit

- **Where:** `pulsern/src/guest.js` · confidence high
- **Problem:** foldPendingProgress calls reconcileProgress(current, snapshot, current). Using the current server state as the old client's baseline makes every stale snapshot difference look like a local edit. For overlapping srsMap entries, mergeScheduleMap therefore selects the snapshot without comparing review timestamps. keepUnmentionedCards only protects cards absent from the snapshot.
- **How it fails:** An old tab holds c1's November 24 schedule. Another device reviews c1 on November 25 and saves its newer interval. The old tab then grades c2 and autosaves its entire blob, including the unchanged November 24 c1 entry. When that parked snapshot is absorbed, c1's newer review is overwritten by the stale schedule.
- **Fix:** Use a snapshot-specific merge for overlapping schedules that preserves the later review rather than treating current as a genuine shared baseline. Add a regression where the old snapshot contains both an unchanged stale entry for c1 and a newly graded c2; assert that c1's newer schedule survives.

### 3. [blocker] Reject pre-reset snapshots before restoring their XP

- **Where:** `pulsern/src/guest.js` · confidence high
- **Problem:** foldPendingProgress continues processing a snapshot even when reconcileProgress rejected it because its reset generation is older. If snapshot.srsMap differs from current.srsMap, the scheduleChanged branch takes Math.max with snapshot.xp, restoring pre-reset XP despite the generation guard.
- **How it fails:** A student with XP and flashcard history resets progress, then records new work, which clears legacy_hold through store.set. An older open tab subsequently autosaves its pre-reset blob and is parked by the revision trigger. On the next load, reconcileProgress correctly keeps the newer reset generation, but scheduleChanged is true for the old flashcard map, so foldPendingProgress restores the old XP total while retaining the reset-era answer history.
- **Fix:** Check reset generations at the start of each pending-snapshot fold and skip older generations before examining schedules, XP, or other fields. Test a generation-1 reset blob against a generation-0 snapshot with higher XP and a nonempty, differing srsMap.
