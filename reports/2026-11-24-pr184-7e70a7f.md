## Assessment

Do not merge. Three persistence defects can corrupt ability/readiness calculations or overwrite newer progress. The supplied tests miss these paths. Tests were not executed during this review.

## Findings

### 1. [blocker] Rewinding answers erases the legacy ability baseline

- **Where:** `pulsern/src/guest.js:467` · confidence high
- **Problem:** replayOrdered reconstructs the prefix using blankScore(base), but replayUnseen skips every legacy row without an attempt ID. Consequently, an out-of-order answer causes the student's accumulated legacy ability to disappear, even though those answers remain in the log. Readiness and adaptive selection then use an ability state inconsistent with the retained history.
- **How it fails:** An existing student has legacy answers plus a newly saved attempt at time 2000. Another device subsequently saves an older attempt taken at time 1000. On reconciliation, the newer attempt is selected for replay, while the legacy prefix is replayed from an empty ability object and silently skipped. The saved category counts and theta values lose the student's pre-update learning history.
- **Fix:** Replay from a preserved checkpoint containing the legacy aggregate state, not blankScore. Preserve non-replayable progress when rebuilding an ordered tail. Add a reconciliation regression with legacy rows, non-default ability, and a delayed older attempt; verify ability and readiness against the correctly ordered result.

### 2. [blocker] Empty-baseline reconciliation drops untested categories

- **Where:** `pulsern/src/guest.js:415` · confidence high
- **Problem:** replayUnseen initializes ability to an empty object when the baseline has no ability map. Replaying answers adds only their categories, and reconcileProgress installs that incomplete map as the complete ability state. overallTheta averages the categories present, so omitted, untested categories no longer pull readiness toward the starting ability.
- **How it fails:** A new account's initial progress insert commits but its acknowledgement is lost. The next answer encounters a revision conflict while loadedBaseline is still empty. Reconciliation replays the answer into ability {}, discarding the seven untouched categories supplied by migrateBlob. After twelve focused answers, readiness is calculated from the practiced category alone rather than all eight categories.
- **Fix:** Seed an empty replay baseline with emptyAbility for the complete category registry before applying answers. Do not seed it with already-updated local theta values. Test an initial lost acknowledgement followed by reconciliation and assert that all eight categories remain present and readiness matches uninterrupted serial execution.

### 3. [blocker] Legacy clients can bypass revision protection and overwrite progress

- **Where:** `pulsern/supabase/migrations/021_progress_revision.sql:2` · confidence high
- **Problem:** Adding a revision column does not enforce revision advancement on database writes. The pre-change application performs an unconditional progress upsert without a revision condition. A tab running that deployed version can still overwrite a row saved by the new client, bypassing the new client's compare-and-swap logic.
- **How it fails:** A student leaves an old-version tab open during deployment, then answers questions in the updated application on another tab or device. When the old tab next autosaves its older whole blob, its existing upsert replaces the newer answers, XP, ability, and schedules. Depending on upsert handling of omitted columns, revision is retained or reset; neither prevents the overwrite.
- **Fix:** Enforce revision advancement server-side, such as with a database trigger rejecting updates that do not advance the revision correctly, or a required CAS RPC with direct incompatible writes denied. Make old clients reload rather than accept unconditional writes. Add a database integration test that attempts the exact pre-change upsert after a newer revision has been saved and verifies that progress is preserved.
