## Findings

### 1. [blocker] Batched record calls overwrite previously scored answers

- **Where:** `pulsern/src/App.jsx` · confidence medium
- **Problem:** record now builds each next state from render-captured log, xp, ability, daily, and streak, then uses replacement setters such as setLog(next.log). Only rewards and run have synchronously updated refs. Two calls before a React commit therefore retain only the second answer in the log and apply only one answer's XP, ability update, and daily increment, while rewards can count both.
- **How it fails:** Starting with an empty account, call record for two correct questions before React renders again. Both calls start from log=[] and xp=0; the resulting saved log contains only the second question. Applying multiple scored readiness-exam items is the important integration path. I could not verify whether the unchanged ExamCenter explicitly forces a React commit between every call; merely awaiting this synchronous record function does not guarantee that. The exam browser tests substitute their own record callback and cannot catch this failure.
- **Fix:** Apply answers through one reducer or another atomic progress-state update that always reads the latest complete state. Add an integration test using the real App record implementation and a multi-item scored exam, asserting every log row, accumulated XP, category ability count, and daily count.

### 2. [blocker] Known bank rows can be mislabeled as built-ins and lose their calibration

- **Where:** `pulsern/src/question-identity.js:41` · confidence high
- **Problem:** stampCatalogQuestion infers origin from an id-and-stem match even when the caller obtained the row from the shared bank. App passes bankQs through this inference without first assigning source='bank'. A seeded bank row matching the bundled question is consequently stamped builtin, and the changed itemRating explicitly ignores its stored bank calibration.
- **How it fails:** The shared-bank query returns question 7 with the same stem as bundled question 7 and elo_rating=1600. It is stamped builtin, so a difficulty-2 question is scored and targeted at the 1300 seed instead of 1600. The learner's Elo/readiness update is wrong, and record also suppresses bank telemetry for that answer. Seeding bundled starter questions makes this a plausible state.
- **Fix:** Stamp source='bank' at the bank-query boundary and source='builtin' at the bundled-content boundary. Preserve explicit origin rather than inferring it from content. Test an actual loaded bank row whose id and stem match a bundled item but whose calibrated rating differs.

### 3. [major] Streak reconciliation counts shielded gaps as additional study days

- **Where:** `pulsern/src/answer-apply.js:58` · confidence high
- **Problem:** reconcileStreak calculates the first streak day as lastDay minus count-1 calendar days. The existing streak count counts studied days, however, and does not include a day bridged by the shield. Calling reconciliation after every live advance can therefore count earlier studied days a second time.
- **How it fails:** Study Monday, miss Tuesday, then answer Wednesday. advanceStreak correctly produces count=2 and consumes the shield. Reconciliation starts at Tuesday, finds Monday in the log, and raises the count to 3. Longer existing runs can be inflated further, affecting shield-refill timing, milestones, and personal bests. This also contradicts the documented promise to preserve existing streak computation.
- **Fix:** Do not apply historical-import reconciliation indiscriminately to live answers. Reconcile imported days using actual studied dates and protected gaps, rather than treating count as an elapsed-calendar-day span. Add an applyAnswer regression covering Monday study, Tuesday absence, and Wednesday shield use.

### 4. [major] Ambiguous legacy IDs silently disappear from Review Misses

- **Where:** `pulsern/src/question-key.js:72` · confidence high
- **Problem:** When a legacy numeric ID appears in both the bundled and bank catalogs, classification marks its history unclassified. settledResult then ignores that history, and scheduleEntry refuses its existing numeric review schedule. The migration retains the bytes but removes the student's outstanding review from the usable review pool.
- **How it fails:** An existing save contains an incorrect answer to id 7 and a pending numeric schedule for 7. Both catalogs contain that number. After classification, Review Misses no longer includes the outstanding miss, and the active bank question can instead appear as new. This affects the common overlapping low-ID range and weakens the protected Review Misses behavior.
- **Fix:** Preserve unresolved pending reviews as an explicit accessible state instead of silently excluding them. Resolve equivalent seeded content where identity can be established, and provide a non-destructive resolution path where it cannot. Add a migration-to-UI test showing that an outstanding legacy miss remains reachable after both catalogs load.

### 5. [major] Today's shift omits outstanding bundled NGN misses after the bank loads

- **Where:** `pulsern/src/App.jsx` · confidence high
- **Problem:** The missesOpen calculation expands historical questions using QUESTIONS only, while QBank uses BUNDLED_QUESTIONS, which also includes NGN_SAMPLES, CALC_SAMPLES, and COVERAGE_SAMPLES. The dashboard and the actual review pool therefore disagree.
- **How it fails:** A student misses a bundled matrix or calculation question while using the fallback bank. Once the shared bank loads, that bundled question is absent from allQuestions. QBank restores it from BUNDLED_QUESTIONS for Review Misses, but the dashboard cannot restore it from QUESTIONS and can show 'No misses to fix' and mark the task complete while that miss remains outstanding.
- **Fix:** Use the same complete bundled registry and review-pool calculation for both QBank and missesOpen. Test a missed bundled NGN item followed by a successful shared-bank load, asserting that Review Misses and Today's shift report the same outstanding work.
