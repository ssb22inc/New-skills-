## Assessment

Two defects remain: passage claims can admit concurrent synthesis after a lease/release race, and permanently refused single-part items do not receive the documented on-screen fallback.

## Findings

### 1. [major] Deleting claims allows generation reuse and concurrent holders

- **Where:** `pulsern/api/_speak.js:293` · confidence high
- **Problem:** The next claim number is derived from files that remain in storage, while releasePassage deletes those files. A stale claimant can therefore create a higher-numbered claim alongside a new, active lower-numbered claim. Both callers return state "mine" and can pay to synthesise the same passage.
- **How it fails:** Holder A has claim 1 and produces no final record after a transient failure. After its lease expires, B reads claim 1 as stale, then pauses before uploading claim 2. A's delayed release deletes claim 1. C now sees an empty directory and acquires a fresh claim 1. B resumes and successfully creates claim 2. On the supported concurrent live/worker path, B and C both find no record and start paid synthesis. The existing concurrency tests do not exercise release and generation reuse between the stale read and upload.
- **Fix:** Use an atomic lease with a monotonic generation and fencing token, such as a database RPC, rather than allocating generations from deletable files. Add a test that pauses a stale takeover after reading the old claim, releases that claim, acquires a fresh claim, and then resumes the takeover; only one new holder must succeed.

### 2. [major] All-refused scripts are treated as temporary outages instead of shown on screen

- **Where:** `pulsern/src/read-aloud.jsx:106` · confidence high
- **Problem:** planReading discards a valid set of silent steps whenever none has an audio URL. Consequently, the documented "Read this part on screen" highlighting works only when another segment has playable audio. A short flashcard side normally has exactly one segment, so a permanent accuracy-check refusal never receives that fallback.
- **How it fails:** A flashcard front fails both voice-check takes and the server saves pass=false. Every subsequent Listen request returns 422. The client reports "The voice isn't available right now. Please try again later," without highlighting the card or displaying "Read this part on screen." Retrying cannot resolve this failed-check record under the current QA version. The all-422 unit assertion currently cements this behavior.
- **Fix:** Distinguish permanent check refusals from transient unavailability. Allow an all-422 script to run its screen-only highlighting sequence, or provide an explicit permanent-refusal state with the documented on-screen instruction. Test a one-segment flashcard refusal and update the all-422 expectation.
