## Assessment

Do not release. The new persistence path can double-credit XP, discard ability evidence during reconciliation, and copy one account's answer history into another after a remote sign-out. These findings are based on the supplied code; tests were not executed.

## Findings

### 1. [blocker] Clear the account-bound store on auth-driven unmounts

- **Where:** `pulsern/src/App.jsx:612` · confidence high
- **Problem:** App cleanup invalidates the save queue but leaves the module-level acceptedBlob, loadedBaseline, accountRead, and progressGate bound to the previous account. store.releaseAccount() runs only through the local sign-out/reset handlers. On a subsequent account load, noteAccountRead rejects the different user at the same epoch, so the previous account's blob remains the autosave merge source.
- **How it fails:** Account A is open in this tab. Another tab signs out, causing AuthGate to unmount App here without calling finishSignOut. The student then signs into a new account B in this tab. B's empty progress read leaves A's acceptedBlob in place. B's initial autosave merges A's log into B's defaults and inserts that history into B's account. This leaks study history across accounts and corrupts B's progress.
- **Fix:** Scope persistence state to the mounted account, or release and abandon its epoch on every auth-driven unmount/account change. Capture the account and epoch before asynchronous reads and reject late completions. Add an AuthGate-level regression test covering remote sign-out followed by signing into a different account with no progress row.

### 2. [blocker] Make XP reconciliation idempotent after a committed write loses its response

- **Where:** `pulsern/src/guest.js:202` · confidence high
- **Problem:** reconcileProgress adds both whole-blob XP deltas from the baseline, even when mergeLogs identifies them as the same attempt. Consequently, retrying an already-committed snapshot can award its XP twice.
- **How it fails:** The loaded baseline has 100 XP. An answer produces a local snapshot with 120 XP. Its database update commits, but the response is lost or exceeds SAVE_ATTEMPT_MS, so the client retains the old baseline/revision. On retry, the conflict read returns that same 120-XP snapshot. Reconciliation computes 100 + (120 - 100) + (120 - 100) = 140 XP, while the answer log contains the attempt only once.
- **Fix:** Make writes/recovery idempotent using a persisted operation identifier, or reconcile credits by unique recorded operations rather than adding overlapping snapshot deltas. Cover flashcard credits as well as question attempts. Add a regression where the server commits a write, its acknowledgement is lost, and retry must preserve exactly the original XP.

### 3. [blocker] Reconcile ability and daily evidence when both devices changed

- **Where:** `pulsern/src/guest.js:201` · confidence high
- **Problem:** When both server and local ability differ from the baseline, reconciliation keeps local.ability wholesale while retaining both devices' answer rows. The same whole-field preference drops concurrent changes to rewards and daily counters. Persisted ability therefore no longer represents the saved answer history.
- **How it fails:** Two devices load a category at n=0. Each answers one different question, producing n=1 locally. Device A saves first; device B encounters a revision conflict. The merged log contains both answers, but ability remains B's n=1 and theta, and its rewards day still counts only one question. Readiness uses two logged answers with only one answer's ability update; the error persists after reload.
- **Fix:** Rebase unique post-baseline answers through deterministic ability updates using their recorded ratings, preserving the legacy ability baseline. Merge additive daily evidence consistently rather than choosing one entire rewards/daily object. Add a two-device conflict test asserting the merged log, ability.n/theta, daily question count, and reward ledger—not just that both log rows survive.
