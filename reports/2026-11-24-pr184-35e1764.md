## Assessment

Not ready to merge. The persistence changes can double-apply historical answers to ability and review scheduling, and can crash when loading valid legacy progress with parked snapshots. The new browser fixture also fails to support the pending-merge reads required by its success paths. Findings are based on the supplied diff; tests were not executed.

## Findings

### 1. [blocker] Resolving a legacy identity can score the historical answer again

- **Where:** `pulsern/src/guest.js` · confidence high
- **Problem:** legacySignature includes row.key, so replayUnseen treats an existing legacy row as a new answer when claimLegacyAt adds its canonical key. If the same save also contains a new attempted answer, reconcileProgress uses replayed.ability, including the duplicate historical update. The replay can also reset the historical miss's review ladder.
- **How it fails:** Start with one legacy Pharmacology miss without an attempt ID, already included in ability.n. Identify that miss in Review Misses, then answer another Pharmacology question before the identity-only save is acknowledged. Reconciliation replays both the newly keyed historical miss and the genuinely new answer: ability.n becomes 3 instead of 2, changing ability and readiness.
- **Fix:** Track baseline answer occurrences independently of editable classification fields. Treat adding source/key to a matched historical occurrence as an in-place correction, not a new scored answer. Add a regression combining identity resolution and a new answer while the resolution save remains unacknowledged, checking ability and review dates against the live sequence.

### 2. [blocker] Pending-merge results bypass legacy-state migration

- **Where:** `pulsern/src/App.jsx:804` · confidence high
- **Problem:** loadProgress initially migrates the saved blob, but replaces that migrated object with absorbPending's result. absorbPending folds acceptedBlob—the raw server blob—and returns it without migrateBlob. A valid pre-update blob and an old-client snapshot can both lack rewards and other additive defaults.
- **How it fails:** An older open app saves twice after migration 022: its first revision-less update advances revision 0 to 1, and its next snapshot is parked. On loading the new app, the initial migration supplies rewards, but absorbing the parked snapshot replaces it with an unmigrated result lacking rewards. applyBlob sets rewards to undefined, and the subsequent rewards.badgesSeen access crashes instead of loading the student's valid legacy save.
- **Fix:** Run the absorbed result through the same validated migration before applying it to React state. Add an integration test with a pre-rewards server blob and a revision-less pending snapshot, asserting that loading succeeds and preserves all legacy progress.

### 3. [major] The browser stub rejects the pending-merge operations used by normal loads

- **Where:** `pulsern/tests/progress-load-browser.test.js:118` · confidence high
- **Problem:** The stub routes progress_pending_merge to the generic offline proxy. Every readable existing progress object now causes store.absorbPending to query that table; the returned error moves the app to the load-error screen. Reset likewise fails on its pending-table deletion.
- **How it fails:** The existing-account handoff tests expect the saved-progress notice and normal navigation, but their successful progress read is immediately followed by an offline pending-merge read. Those tests time out before exercising their assertions. The reset tests also cannot reach the progress-row deletion.
- **Fix:** Implement progress_pending_merge SELECT and DELETE behavior in the browser fixture, returning an empty successful result by default and allowing scripted pending snapshots. Preserve revision values in progress reads so conflict-recovery tests exercise the real adapter contract.
