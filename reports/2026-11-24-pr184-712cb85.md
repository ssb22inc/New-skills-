## Assessment

Do not ship yet. Static review found five concrete persistence and account-isolation defects, including lost progress and a cross-account history leak. The warfarin correction is appropriate; no new clinical error was identified in the attached images.

## Findings

### 1. [blocker] Scope accepted progress and revisions to the account that loaded them

- **Where:** `pulsern/src/App.jsx:357` · confidence high
- **Problem:** acceptedBlob and progressGate are module globals shared by every App mount. Progress reads are neither cancelled nor account/epoch-checked before updating those globals. AuthGate remounting App for another user does not isolate them.
- **How it fails:** Account A's progress SELECT is delayed while an auth change switches this tab to account B. B's SELECT completes first, then A's response replaces acceptedBlob and the revision. B's next save calls blobForSave with A's history. If the revisions match, the write succeeds under B's user_id and copies A's answer history into B's account.
- **Fix:** Keep accepted blobs and revision state account-scoped. Capture the user and epoch before each read, reject responses from an abandoned account, and invalidate reads and writes on account change/unmount. Add a deferred two-account read test that verifies no A data can enter a B write.

### 2. [blocker] Preserve progress changes that do not append a question answer

- **Where:** `pulsern/src/guest.js:166` · confidence high
- **Problem:** reconcileProgress takes XP, streak, rewards, daily, ability, bestRun and missSchedule from the server and only changes them by replaying pending log rows. ANSWER_FIELDS prevents local changes to those fields from being merged. blobForSave invokes this on every ordinary save, not just conflicts. Migration-provided defaults can also be discarded when absent from the raw server blob.
- **How it fails:** After an account has a saved row, grade a flashcard Good after the time floor. srsMap saves, but the earned 5 XP, card ledger and streak change are discarded because no question row was appended. applyBlob then rolls the visible values back. Reward preferences, promotion markers and session bests are discarded in the same way. A legacy save without ability also loses the full category defaults supplied by migrateBlob.
- **Fix:** Reconcile all supported progress mutations against a migrated baseline, including card grading/undo, reward preferences and markers, streak changes, and schedule changes. Preserve migration defaults. Add real-App save-and-reload tests for a flashcard grade, undo, preference change and a legacy blob without ability.

### 3. [blocker] Do not replay legacy identity corrections as new answers

- **Where:** `pulsern/src/guest.js:165` · confidence high
- **Problem:** For rows without attempt IDs, progressRowKey includes row.key. claimLegacyAt changes that key on an existing historical row, so reconciliation considers the edited row a pending new answer. It retains the original unresolved row and calls applyAnswer on the replacement.
- **How it fails:** A student identifies an ambiguous historical miss as builtin:7. On save, the unresolved miss remains and another incorrect answer is appended. Ability is penalized again, answer counts increase, and the unresolved review returns. Undated rows are additionally replayed against the hard-coded 2026-11-24 date.
- **Fix:** Represent legacy identity resolution as an update to an existing historical record, not an appended attempt. Use stable record identity or baseline-aware row updates, and merge the associated schedule change without invoking answer scoring. Test choosing a candidate through the real UI, then saving and reloading with unchanged log length and ability.

### 4. [blocker] Report an unavailable storage adapter as a failed guest save

- **Where:** `pulsern/src/guest.js:46` · confidence high
- **Problem:** saveGuest returns true when storage is null because the optional setItem call does nothing and execution still reaches return true. localBox explicitly returns null when accessing localStorage throws.
- **How it fails:** A visitor with browser storage disabled completes the trial. The save screen says the answers are saved on this device for seven days, although they exist only in memory. Reloading or leaving the tab loses them without the warning intended for an unsuccessful device save.
- **Fix:** Return false when a usable storage adapter is absent, and apply the same distinction to holdGuestTrial. Test saveGuest(null, guest) and a browser whose localStorage getter throws; the screen must show the non-persistence warning.

### 5. [major] Stop reconciliation from creating an endless autosave loop

- **Where:** `pulsern/src/App.jsx:718` · confidence high
- **Problem:** The autosave payload omits run, but reconcileProgress always adds run to its output. Once acceptedBlob exists, store.set therefore reports reconciled on every save. The callback unconditionally calls applyBlob, which creates a fresh srsMap through migrateLegacySrs. That dependency change schedules another autosave.
- **How it fails:** Load an account and leave the page idle. After the first accepted save, saves continue indefinitely without student activity, repeatedly updating the progress revision and issuing database writes.
- **Fix:** Exclude transient fields such as run from persisted reconciliation comparisons, and only rehydrate when persisted state meaningfully differs. Avoid replacing equivalent state objects during rehydration. Add an integration test that waits for initial persistence and asserts that writes stop while the app is idle.
