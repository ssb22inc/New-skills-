## Findings

### 1. [major] Bank-side account errors incorrectly trigger another run

- **Where:** `pulsern/ops/read-aloud-worker.mjs:432` · confidence high
- **Problem:** The setup check recognizes account errors from the queue through q.service, but not from prewarmBank. Bank-side 401, 403, and 404 responses become w.failure=true with a stopped message such as "provider: speech 401". If any passages were completed earlier, progress is true and the failed run chains despite the explicit promise that account/setup failures never chain.
- **How it fails:** Several passages are voiced successfully, then a bank synthesis receives HTTP 401. runJob returns setup=false and more=true, causing another paid-environment workflow dispatch after the pause instead of stopping for the account problem.
- **Fix:** Return an explicit service/setup indicator from prewarmBank and include it in runJob's setup calculation. Add a regression test with successful passages followed by a bank-side 401 or 403, asserting more=false.

### 2. [major] The recovery pause can consume the remaining job timeout

- **Where:** `.github/workflows/pulsern-read-aloud.yml:76` · confidence high
- **Problem:** The new 10-minute sleep runs inside the existing 40-minute job timeout. No worker runtime limit reserves those ten minutes, so a failed worker that finishes after roughly 30 minutes can report more=true but have its continuation step killed before dispatching the next run.
- **How it fails:** The serial voice worker completes passages for 32 minutes, then encounters a storage failure and exits with progress=true and more=true. The continuation sleeps for ten minutes, but GitHub terminates the job at minute 40 before the gh command runs. The intended recovery is lost.
- **Fix:** Reserve execution time for the backoff and dispatch by bounding the worker's runtime and adjusting the job timeout, or implement the delayed continuation outside the expiring job. Verify a late failure with progress still reaches dispatch.
