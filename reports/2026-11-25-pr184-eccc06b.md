## Findings

### 1. [minor] foldPendingProgress does not use applyAnswer

- **Where:** `pulsern/src/guest.js` · confidence low
- **Problem:** Direct duplicate scoring path in `foldPendingProgress`.
- **How it fails:** If progress_pending_merge ever contains a row with `legacyRepeat` (or another future per-row XP marker), the `foldPendingProgress` merge re-scores that row with `answerXp()` directly instead of routing through `applyAnswer()`. `answerXp()` does not honor `legacyRepeat`, so the credit that was deliberately suppressed could be paid again, and ability would be updated when the original answer did not update it. Pre-PR snapshots lack that field, so this path is likely not reachable today, but the parked-merge machinery is now the general conflict path and should keep the same scoring entry point as live answers.
- **Fix:** Route each new row through `applyAnswer` or filter out `legacyRepeat` rows before the direct XP/ability replay.

### 2. [minor] Guest save screen overstates rank progress

- **Where:** `pulsern/src/guest.jsx` · confidence medium
- **Problem:** SaveProgress next-rank copy omits non-XP requirements.
- **How it fails:** The guest save screen says “{sum.xp} of {next.xp} XP toward Graduate Nurse” as the sole progress indicator, but the next rank also requires 20 answered questions. A guest with 5 answers and, say, 80 XP from difficulty 3 items would be told they are at the XP threshold while the real gate still needs 15 more answers. This is user-facing copy that the code does not make true.
- **Fix:** Mention the answer-count requirement and show both metrics (e.g., “{sum.xp} of {next.xp} XP and {sum.n} of 20 answers”).

### 3. [minor] SIGNED_OUT handler may delete an active trial

- **Where:** `pulsern/src/auth.jsx` · confidence low
- **Problem:** Overly broad guest-trial clearing on all SIGNED_OUT events.
- **How it fails:** The `AuthGate` `forgetTrial` callback clears `pulsern-guest-v1` on every `SIGNED_OUT` event, including a supabase token refresh sign-out (e.g., a forced re-login from another tab or an OAuth callback). If a student was in the middle of the guest trial and a transient `SIGNED_OUT` event fires before sign-in completes, the device trial is deleted. The one-time forced re-login already clears the key intentionally when a session exists, but this broad handler triggers on every `SIGNED_OUT` even when no user-initiated sign-out occurred.
- **Fix:** Only clear the guest trial on user-initiated sign-out paths (`signOutAndForgetTrial` and the forced re-login), or distinguish a remote-session drop from an intentional sign-out before deleting.
