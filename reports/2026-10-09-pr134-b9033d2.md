## Assessment

Do not merge. The new publication gates still accept forged approval metadata and editable cached decisions, and the freshness key misses part of the rendering dependency graph. These gaps can publish content without the intended review. I reviewed the supplied diff only; I could not run CI or verify GitHub environment and branch-protection settings.

## Findings

### 1. [blocker] The CI publication guard accepts fabricated visual-review signatures

- **Where:** `pulsern/tests/diagram-gate.test.js:164` · confidence high
- **Problem:** The configured CI has no DIAGRAM_ATTEST_KEY, so this critical guard checks only that sig contains 64 hexadecimal characters. The verdict, sourceKey, frame list and map fingerprints are all publicly computable. The paid mapper's signature verification does not protect a map committed directly to the branch.
- **How it fails:** Add a pairing to item-map.json and an index entry containing the current sourceKey, expected frames, verdict PASS and sig set to 64 zeroes. This publication test passes despite no visual review having occurred, and pairsFor displays the diagram because it checks only the question and diagram fingerprints.
- **Fix:** Use signatures that a trusted publication check can actually verify without exposing a signing secret, such as asymmetric signatures with a protected public verification key. Require verification for every published diagram and add a negative fixture proving that a well-shaped but fabricated signature fails the actual CI publication path.

### 2. [blocker] Editable pairing-cache records can publish unconfirmed patient values

- **Where:** `pulsern/ops/map-diagrams-lib.mjs:160` · confidence high
- **Problem:** publishable authenticates the diagram's visual approval but not the pairing decision. It checks public content hashes and extracted values, then passes the entire editable record through. buildItemMap copies d.shown directly. Neither attach nor shown is authenticated, and shown is not checked against extracted and values_confirmed.
- **How it fails:** After a legitimate pairing review, change only shown in reports/diagram-map/decisions.json to a different patient's ABG values, leaving extracted and the hashes unchanged. The trusted mapper skips the model call because isFresh and sameProposal pass, then publishes the altered values with freshly computed question and diagram fingerprints. The student sees values that the pairing reviewer never confirmed. Changing a cached rejection to attach:true similarly bypasses the pairing review.
- **Fix:** Authenticate complete pairing decisions before either reuse or publication, binding the question, diagram content, extracted values, attach decision and value-confirmation result. Derive shown from the authenticated extracted values and confirmation flag rather than trusting a separate cache field. Test both rejected-to-attached and shown-value mutations.

### 3. [blocker] A fabricated manifest entry skips audio QA and plays the wrong recording

- **Where:** `pulsern/ops/narrate.mjs:132` · confidence high
- **Problem:** isCurrentClip treats editable manifest metadata as evidence that audio passed QA. A matching input id, current qa number and hash-shaped URL filename do not establish that those audio bytes say the step's script. audioFor likewise trusts the editable textFp field, and the shipped-manifest tests do not verify the script-to-audio association.
- **How it fails:** Copy a real potassium recording's URL and audio hash into an ABG step, and set id and textFp to the publicly computable values for the ABG script. Keep qa at QA_VERSION. The trusted narration job considers the entry unchanged and performs no transcription; the client then plays potassium narration over the ABG lesson. The content-addressed URL remains valid throughout, so immutable storage does not prevent this substitution.
- **Fix:** Record an authenticated audio-QA attestation binding the audio-byte hash, exact script digest and QA version. Verify that attestation before skipping a clip and before publication, or fetch and recheck unauthenticated existing clips. Add a regression test that swaps two valid recordings while updating manifest metadata.

### 4. [blocker] The freshness key does not follow dependencies of the actual registry entry point

- **Where:** `pulsern/ops/diagram-attest.mjs:201` · confidence high
- **Problem:** sourceKey hashes top-level diagram files, but its transitive walks start only at each diagram JSX file and explainer.jsx. It never traverses src/diagrams/index.js or match.js, although the renderer and application load the registry through index.js. A helper imported only by the registry can therefore affect the shipped diagram without appearing in diagramSources or changing sourceKey.
- **How it fails:** The registry imports a helper under src/clinical/ and uses it to supply an ABG dynamicCaption or wrap a diagram. After a legitimate review, change that helper's interpretation for a non-example value. The registry file and diagram JSX files remain unchanged, so the existing signed approval and map remain current. diagramFp also excludes dynamicCaption, allowing the changed interpretation to reach students without a fresh diagram review.
- **Fix:** Build the dependency closure from the actual renderer/application registry entry point and the matcher entry point, not only the individual JSX definitions. Include those resolved dependencies in both the review request and freshness key. Add a fixture where changing a helper imported solely by index.js invalidates an existing approval.
