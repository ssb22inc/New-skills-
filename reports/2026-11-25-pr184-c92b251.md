## Findings

### 1. [major] legacyHold leaks across accounts because store.insertAt and releaseAccount do not reset it

- **Where:** `src/App.jsx` · confidence medium
- **Problem:** User A resets progress (store.delete sets the module-level legacyHold to true), then signs out. releaseAccount() does not reset legacyHold, and a subsequent insert for user B uses legacyHold in the row (insertAt sets legacy_hold: legacyHold), while the code does not clear it after a successful insert either. On a shared browser, user B's first progress row is created with legacy_hold=true, so migration 022's trigger returns old without parking revision-less snapshots; an older open tab's unsaved answers are dropped (data loss) instead of being merged later. Set legacyHold=false in releaseAccount, on successful insert, and when loading/starting a new account.
- **How it fails:** Shared device: A resets and signs out; B signs in without reload. B's first row is inserted with legacy_hold=true. A revision-less old-app save from B's older tab is ignored rather than parked, losing answers.
- **Fix:** Reset legacyHold=false whenever the account epoch changes (releaseAccount) and after a successful insert (store.set insertAt branch); consider carrying it as per-account state rather than module global.
