## Findings

### 1. [major] Active exhibits remain collapsed during screen-only reading

- **Where:** `pulsern/src/App.jsx:1578` · confidence high
- **Problem:** Only the first exhibit is opened. Reading a later exhibit adds a highlight to its details element but does not reveal its content. This breaks the fallback that tells students to read a refused passage on screen.
- **How it fails:** A question has two exhibits. The second exhibit receives a 422 voice-check result while other passages are playable. When playback reaches that exhibit, the app displays "Read this part on screen" and runs its reading timer, but the clinical text remains hidden inside the collapsed details element.
- **Fix:** Reveal an exhibit before playing or timing its active passage, while preserving the student's manual expansion choices. Add a mounted test with a second exhibit whose audio is refused; assert that its body is visible while highlighted.

### 2. [major] Bank prewarming immediately retries work deferred by the queue

- **Where:** `pulsern/ops/read-aloud-worker.mjs:327` · confidence high
- **Problem:** A queued transient failure sets q.operational but does not prevent prewarming. Prewarming checks only for a completed record, not an existing retry entry, so it can synthesize the same passage again immediately. Queue attempts and cursor attempts are independent, defeating the documented five-attempt limit per passage.
- **How it fails:** Speech synthesis succeeds for one passage but its transcription repeatedly fails; other passages succeed. The queue moves that passage to queue-retry, then prewarming reaches the same bank item and pays for another synthesis in the same run. Across five runs this can produce nine paid syntheses before the queue's fifth attempt finally writes a give-up record.
- **Fix:** Ensure prewarming does not synthesize passages already awaiting queued retries, and use one attempt count per passage across both paths. Alternatively, stop prewarming after an operational queue failure. Add a runJob test that exercises both paths against the same failing passage.

### 3. [major] QA-record read outages are treated as cache misses

- **Where:** `pulsern/api/_speak.js:403` · confidence high
- **Problem:** readRecord uses readJson, which returns null for every download error, including storage 500s. The worker cannot distinguish an absent record from an unreadable existing record, so it can spend again and report a successful run despite the storage failure.
- **How it fails:** During a bank scan, downloading an existing passage's QA JSON returns a transient 500 while counter operations and uploads still work. Prewarming treats the already-checked passage as unvoiced, pays to synthesize and transcribe it again, overwrites its record, and leaves runJob.failed false. A record-download outage can repeat this across cached passages until the daily budget is consumed.
- **Fix:** Distinguish missing objects from operational read failures. Propagate record-read failures so the route returns an availability error and the worker preserves work and fails the run without synthesizing that passage. Test a QA-record download failure separately from a missing record.
